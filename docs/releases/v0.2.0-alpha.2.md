# Omarchy 4 Pi — 4GB-first Alpha 2

An experimental flashable image for **Raspberry Pi 4 Model B with 4GB+ RAM**. Not an RC, not a replacement for the current stable image, and not a claim of Raspberry Pi OS benchmark parity. Test on a spare card; keep your working installation as rollback.

## What is in this alpha

- Stock clocks by default, with an implemented opt-in CPU tuner: firmware boost and experimental 1.8/1.9/2.0GHz targets. Interactive confirmation, exact config backups, post-reboot confirmation, and a temperature/voltage guard. No voltage overrides, forced turbo, GPU overclock, or weakened thermal limits.
- Load-responsive CPU scaling at boot where supported, without an always-running governor daemon.
- Explicit Pi compressed swap and app-scope OOM policy, independent of upstream's ARM packaging exclusions. Approximately half of RAM is logical zram capacity, using the kernel-supported default compressor.
- Bounded journal retention and smaller SD-card writeback bursts. Persistent diagnostic logging stays enabled.
- At most two default compiler jobs on a 4GB desktop, RAM-aware reductions, and bounded level-3 local package compression.
- Resource-scoped agent/build jobs, JSON hardware reports, and a short temperature-guarded CPU microbenchmark.
- Fork/ARM update safeguards, pinned reviewed package recipes, retryable core installs, and an installed-source receipt that avoids rebuilding an already-installed source commit.
- The missing screensaver renderer is required and audited; renderer failure exits instead of entering a log loop.
- New Omarchy-inspired README artwork.

## Flash with Imager customization

Use Raspberry Pi Imager 2.0.11 or newer. On macOS:

```bash
open -n -a "/Applications/Raspberry Pi Imager.app" --args --repo \
  "https://github.com/pkyanam/omarchy-4-pi/releases/download/v0.2.0-alpha.2/os-list.json"
```

Select Pi 4 and the alpha image, then your target card. **Writing erases the target.** Set your chosen hostname (for example `omarchy-pi`, without `.local`), account, network, and SSH options through the Imager wizard. Hostname provisioning uses systemd and mDNS waits for it; existing regression tests cover that ordering and failure handling. Verify the actual hostname after boot, rather than interpreting a cached mDNS response as proof it changed.

## First boot: leave clocks alone initially

```bash
hostnamectl --static
omarchy-pi-check
omarchy pi report --json
zramctl
swapon --show
systemctl --failed
```

Check the display, network, audio, keyboard/mouse, lock/wake, and a second reboot. Then optionally compare repeated `omarchy pi benchmark --seconds 30` samples. Clock trials are optional and need cooling, a healthy PSU, a whole-card backup, and a card reader. Read the [tuning and physical recovery guide](https://github.com/pkyanam/omarchy-4-pi/blob/main/docs/pi-tuning.md) before `omarchy pi tune apply`.

## Already running the original release?

You can upgrade in place without reflashing, but the original `v0.1.0-rc.1` updater needs a [one-time bootstrap](https://github.com/pkyanam/omarchy-4-pi/blob/main/docs/pi-upgrade.md) to reconcile the new runtime packages and Pi policies. Thereafter use `omarchy update`. This follows the fork's `main` branch and rolling ARM packages, not a selected release tag. Back up first; a reboot is required for boot-time policies. Owner setup is not replayed and overclocking is not enabled by an update. The full original-card upgrade still needs hardware validation.

## Validation boundaries

The [native ARM64 factory run](https://github.com/pkyanam/omarchy-4-pi/actions/runs/33936036127) succeeded with **139 image invariants verified**. An independent download on macOS matched both the compressed SHA-256 and the entire decompressed 12GiB image hash. Both public image/catalog URLs returned HTTP 200, and the stable release remains Latest.

- Image: `omarchy-4-pi-20260905-33d01b75-minimal.img.xz` (2,051,339,156 bytes).
- Clean image source: `33d01b75d3acca18a0307a80f7780b355ac91b1b`.
- Download SHA-256: `be49f9229d2851823c0bbbaf050988f9911590db855ea0dfaea30b26e13c54d5`.
- Extracted-image SHA-256: `029b9a7645df18fb0ce916b9d8fd31e0f9e2ecc286bbc26fdf59615ba46c2ea2`.
- Manifest confirms `ttfx 0.3.2-1`; catalogs agree on the image and `rpi-preseed` customization.

The alpha.1 factory attempt stopped before publication when package downloads filled the 12GiB staging filesystem. Alpha.2 keeps those temporary downloads on the builder's external workspace, with regression coverage for cache placement and cleanup. The image size is unchanged; no package-signature or filesystem check was relaxed.

The release pipeline runs focused Pi regressions, builds on native ARM64, audits the assembled root filesystem, checks clean filesystems and AArch64 payloads, parses the Hyprland configuration, and validates device-first Imager catalogs. Assets include checksums, build provenance, and the image audit. Local checks additionally exercise the CLI suite, service-unit parsing, real zram unit generation, and 22 clock/benchmark tests.

These are software/build checks, not a successful physical boot of this new image. Actual 4GB Pi memory behavior, sustained performance, governor transitions, and clock trials still need hardware testing. The established ALARM kernel/firmware boot path is retained; the separately investigated Pi OS vendor-kernel/media variant is not included. A short benchmark or a clear temperature reading does not certify an overclock as safe.
