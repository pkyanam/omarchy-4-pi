# Independent final review of the Omarchy 4.5 Pi 4 candidate

Reviewed merge `496429ba17bc0bccc1711e8c2c8586fcdde3953c` against fork baseline `393f48c3` and released upstream `ac2690cd7be4f47e4a255f5e2e78d904d436b068`, including the reported follow-ups through `9bda36bb`. Scope was package trust/dependencies, image assembly and cleanup, first boot, provisioning retries, update receipts/guards, and Pi resource defaults. No production/test edits, Git mutations, containers, services, builds, or physical/UI operations were performed by this reviewer. This report is the only retained edit.

Findings at the reviewed commit, ordered by impact (parent follow-up below records subsequent fixes):

1. **P2 — Exact installed-core dependencies prevent the next reviewed runtime-pin transition.** `build-packages-rpi4.sh:65` embeds exact Hyprland, titlebar and Quickshell versions in the local core's hard dependencies. `bin/omarchy-update-system-pkgs:42` upgrades the runtime while `IgnorePkg` retains that old core; `bin/omarchy-update-rpi4:60` rebuilds its replacement afterward. When reviewed source changes a pin, such as Hyprland `0.56.2-7` to `0.56.2-8`, the first transaction cannot satisfy the installed core's old dependency and never reaches the matching rebuild. This is new in the integration and does not prevent a fresh image using today's pins. Remedy: include the compatible local pair and changed runtime in one dependency-checked transaction, or redesign the core constraints and reconciliation together. Validate a pin change with real libalpm and the old core installed; the passing order mocks do not model these reverse dependencies.

2. **P2 — A partially completed fresh installation cannot resume through its installer.** `install-rpi4.sh:114` rejects any existing core/profile/provisioning directory as an already provisioned system. However, `install-rpi4.sh:355` installs the core and writes the profile before `run_system_setup` at line 358. A required system-setup failure or failed OEM Node download therefore leaves a fresh installation whose next installer invocation is refused. The suggested updater does not finish system/OEM setup, and a candidate branch intentionally cannot use production updates. This refusal is new relative to `393f48c3`. Remedy: distinguish an installer-owned incomplete checkpoint from a completed installation and provide a validated resume path, while preserving the legacy/completed-install refusal. A disposable factory rootfs can instead be discarded and rebuilt.

3. **P2 — Copied macOS local catalogs retain container-only image URLs.** `image/build-rpi4-image.sh:644` now generates local file catalogs by default. In the Mac wrapper those URLs identify `/output/<image>.img.xz`; `image/build-rpi4-image-macos.sh:173` copies the catalogs to the host without rebasing them. Raspberry Pi Imager on the Mac cannot open that image URL after container cleanup. A tiny disposable fixture using the real generator/validator passed in its original directory, then failed after the same copy operation with `url points outside the local asset directory`. This local-catalog default is new. Remedy: rewrite file URLs to the host output directory after copying, preserve the recorded hashes, and validate there. The existing Mac Imager launcher regenerates its own catalog and provides a workaround. No image-byte rebuild is needed for this fix.

- **P2, resolved:** standalone `install-rpi4.sh --image` staged Node but did not create the full factory manifest required by `install/user/mise-work.sh`. Staging now retains a verified bundle receipt; preload uses it only when the full manifest is absent. The parent reports the real staging/preload regression passing in `build/validation/linux/rpi45-mise-offline-review.log`, including tampering and malformed-present-manifest rejection. These checks were not rerun by this reviewer.

The superseded provision failure in `final-followup-tests.log` is not an outstanding failure; `linux/rpi45-provisioning.log` is the passing follow-up.
