# Omarchy 4.5 Pi 4 image implementation

Implemented on the shared `codex/omarchy-4.5-pi4` working tree. This agent changed only image-owned paths, first-boot hardware integration, image-specific unit drop-ins, and uniquely named image regression tests. No index, checkout, branch, merge, commit, push, release/tag, host installer/update, container/build, or device operation was performed. Temporary Git plumbing in fixtures operated only inside disposable directories. Physical Pi 4 4GB/8GB qualification and Pi 5 support are not claimed.

## Result

- **F3:** `image/rpi4-manifest.py` encodes JSON and strictly rejects duplicate keys, non-JSON constants, unknown/missing schema fields, wrong types, unreviewed recipe identity, inventory mismatches, Node tampering, and changed source snapshots. `package_repository` is an array of installed server URLs. Validation covers exact source HEAD/branch/origin/observed tracking ref, source tree SHA-256, upstream release commit, recipe pin, every installed package/version, signed base digest/signer, and offline ARM64 Node filename/hash. Only parsed, checked clean source receives `/var/lib/omarchy/rpi4-source-commit`; a dirty candidate carries explicit dirty provenance and no clean receipt. Embedded and downloadable manifests are copied byte-for-byte.
- **F7:** `image/workspace.py` creates a unique `omarchy-rpi4-*` child with a per-invocation ownership sentinel under `OMARCHY_IMAGE_WORK` (now a parent, default `/var/tmp/omarchy-images`). Cleanup validates the child, sentinel, owner, path components, and remaining mountpoints. It never deletes the caller parent. Root/home/repository/output overlap and symlinks are rejected. Only verified disk filesystems are accepted, with byte/inode preflights; btrfs's zero/unbounded inode pool is supported.
- **F8:** the catalog generator uses a JSON encoder; optional asset-directory validation checks complete image existence, filename correspondence, size, and SHA-256. Release staging copies a catalog only when it stages the matching whole image. Split mode removes stale whole-image/catalog promises and documents checksum/reassembly plus `generate-local-imager-manifest.sh` / `open-in-rpi-imager-macos.sh` to preserve Imager customizations. The workflow validates staged assets before any release mutation and no longer blindly copies all original catalogs. The workflow was edited and parsed only; it was not triggered.
- **F12:** before install/system apply the factory writes trusted root-owned `format=1`, `platform=aarch64` to `/var/lib/omarchy/image/target`. Generic hardware stays queued instead of applying the ARM builder's identity. The factory separately runs the Pi-only KMS/module/performance leaf and enables Bluetooth before audit/first boot. It runs explicit mkinitcpio and the actual image's ARM Hyprland parser as the unprivileged builder. After package operations it kills keyring agents, removes the entire factory pacman keyring, preserves packaged public trust, and arms `/var/lib/omarchy/image/pacman-keyring`. The serialized upstream hardware runner creates/populates a fresh identity before hardware leaves; this change additionally rejects symlinked/untrusted keyring requests and paths.

## First-boot and package coordination

The factory installs these two new drop-ins:

- `install/provisioning/omarchy-provision-hardware-rpi4.conf` → `/etc/systemd/system/omarchy-provision-hardware.service.d/10-rpi4-grow-root.conf`: `Requires` and `After` root growth.
- `install/provisioning/omarchy-provision-owner-rpi4-image.conf` → `/etc/systemd/system/omarchy-provision-owner.service.d/20-rpi4-image-hardware.conf`: `Requires` and `After` hardware/keyring setup, plus `[Service] Environment=OMARCHY_PATH=/usr/share/omarchy` before uwsm exists.

The existing grow-root-before-owner `Requires`/`After`, owner-before-SDDM `Requires`/`After`, and Avahi owner-hostname ordering remain. The resulting intended chain is growth → hardware/keyring → owner → SDDM; Avahi also waits for owner. Owner's direct serialized hardware call protects manual retries. Linux systemd transaction/cycle validation is still a gate.

The pre-installer signed sync calls package-owned `omarchy_pi_bootstrap_keyring` in the chroot with `TMPDIR=/mnt/omarchy-build/tmp` before `-Syyuu`. Its reviewed SHA-512 public trust inputs come from [omarchy-pkgs c7a1ef7f](https://github.com/omacom/omarchy-pkgs/blob/c7a1ef7f86cccab072fb11f22564862c03f50199/pkgbuilds/omarchy-keyring/PKGBUILD); no executable recipe is evaluated as root and signatures remain required. The factory uses the package agent's stable ARM templates and passes `OMARCHY_PI_BUILD_PARENT=/mnt/omarchy-build/tmp` into the installer. Installer/core builder own `omarchy_pi_prepare_build`, makepkg config/cache artifact collection, and cleanup; the image factory has no direct makepkg invocation.

**Package bootstrap ownership resolved:** package-owned `omarchy_pi_bootstrap_keyring` now removes its unowned public source files after importing/populating trust and preserves already package-owned files. That avoids the later signed `omarchy-keyring` installation conflict in both factory and installer paths. The factory uses that shared implementation without duplicating its cleanup. Native libalpm still needs to verify the actual transaction.

The mounted-root audit now checks the stable policy marker/mirror, required signatures/public trust, local core/settings `4.5.0.pi4.1-1`, reviewed Hyprland/titlebar/Quickshell versions, new capture/media/application/input/runtime packages, the AArch64 titlebar plugin, deferred trusted image/keyring state, owner environment/dependencies, absent factory pacman identity, effective managed Pi firmware policy, no generic boot fragments, and no overriding vendor zram policy. It also distinguishes firmware-loaded `kernel8.img` (U-Boot) from `/boot/Image` and the Linux DTB under `/boot/dtbs/broadcom`, matching [ALARM's U-Boot script](https://raw.githubusercontent.com/archlinuxarm/PKGBUILDs/master/alarm/uboot-raspberrypi/boot.txt.v3). Package metadata is read once rather than spawning awk thousands of times. The existing actual ARM Hyprland parser gate remains mandatory. These checks do not prove a hardware renderer or decoder.

## Candidate lineage

Native source builds require an unconflicted checkout containing exact released commit `ac2690cd7be4f47e4a255f5e2e78d904d436b068`. The macOS wrapper verifies that ancestry before Docker work, creates a shallow private Git object store for the exact local commit, and transfers it beside the working snapshot. Local refs make unpublished commits fetchable without contacting a public branch. Source overrides cannot replace a native checkout's actual HEAD.

An unpublished `codex/omarchy-4.5-pi4` checkout keeps that name and its actual observed remote ref (normally absent); no `origin/main` is manufactured. Such outputs receive `-candidate` in the basename. Dirty snapshots are identified and hashed explicitly. With no explicit `OMARCHY_IMAGE_DOWNLOAD_BASE_URL`, artifacts get a local file catalog instead of pretending to exist under a published latest URL. A candidate branch is deliberately outside the production updater's main-branch contract; do not rewrite refs to bypass that guard.

For a transferred raw snapshot outside Git, direct Linux invocation requires `OMARCHY_SOURCE_REPOSITORY` pointing to a local shallow object store, `OMARCHY_SOURCE_COMMIT`, `OMARCHY_SOURCE_BRANCH`, `OMARCHY_SOURCE_ORIGIN`, `OMARCHY_SOURCE_DIRTY=true|false`, optional actual `OMARCHY_SOURCE_TRACKING_COMMIT`, and `OMARCHY_SOURCE_UPSTREAM_COMMIT=ac2690cd7be4f47e4a255f5e2e78d904d436b068` after ancestry was checked in the original checkout. The Mac wrapper supplies these. A plain source tarball with invented Git metadata is not a supported build input.

## Exact build prerequisites

1. Parent resolves and commits the integration, including reviewed recipe pin `c7a1ef7f86cccab072fb11f22564862c03f50199`, complete stable runtime closure, and current provisioning/performance interfaces. Do not build the still-conflicted merge.
2. Use one coordinated native AArch64 Linux build, root with loop devices/private mount namespaces, on a real disk mount. Required host commands: `blockdev`, `bsdtar`, `chroot`, `curl`, `e2fsck`, `findmnt`, `fsck.vfat`, `git`, `gpg`, `losetup`, `mknod`, `mount`, `mountpoint`, `mkfs.ext4`, `mkfs.vfat`, `parted`, `python3`, `rsync`, `sha256sum`, `sha512sum`, `udevadm`, `umount`, `xz`, `zerofree`, plus ordinary coreutils/util-linux. `image/Dockerfile.builder` now includes Python 3.
3. Default image size remains 12 GiB. A shared workspace/output filesystem needs at least `2 * image_size_gib + 12` GiB free (36 GiB at default) before downloads. On separate filesystems the work floor is `image_size_gib + 12` GiB and output is `image_size_gib + 1` GiB; account for shared physical backing separately. Work needs 50,000 free inodes unless btrfs reports an unbounded pool. These are planning floors, not measured peak guarantees.
4. The Mac wrapper checks host free space, uses the engine's native ARM architecture/CPU/RAM inventory, and creates a unique private disk volume for staging, without changing global VM settings. Defaults are at most two workers, limited by VM CPUs; container memory is VM RAM minus 512 MiB capped at 4096 MiB. It enforces CPU/cpuset and memory/no-extra-swap limits. On the parent's 1-CPU/2-GiB OrbStack allocation that means one worker and roughly 1.5 GiB container RAM. Actual package/linker peaks may still require stopping and coordinating a revised explicit budget.
5. Native factory defaults to one compiler worker. Make/CMake/Cargo/Go hints propagate into the builder; Cargo uses `CARGO_BUILD_JOBS`. Compression defaults to one xz worker and 512 MiB, configurable via `OMARCHY_XZ_THREADS` and `OMARCHY_XZ_MEMORY_MIB`; `XZ_OPT`/`XZ_DEFAULTS` cannot override them. Native non-container runs need an equivalent outer memory limit supplied by the parent.
6. Installer/core work uses the performance helper's current-shell, private disk-backed environment. The parent's `omarchy45-validation-work` btrfs volume can supply sibling source/work/output paths for a direct Linux build; give `OMARCHY_IMAGE_WORK` its own parent rather than the volume root when source/output are also on that volume. No volume was created or changed by this agent. `--keep-work` retains the owned child, and the Mac wrapper retains its private workspace volume when requested.
7. Network access is needed for the signed ALARM base and signature, reviewed public keyring inputs, immutable reviewed recipes, stable signed binary closure, and checksum-verified ARM64 Node bundle. Offline first boot is supported by retained public vendor keyrings, installed runtime packages, and `node_bundle.filename` / `node_bundle.sha256`; it still needs Linux/board validation.
