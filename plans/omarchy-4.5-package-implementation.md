# Omarchy 4.5 Pi package implementation

Implementation in the assigned package/install/update paths is complete for parent review. Only bounded macOS fixtures and read-only source/repository metadata checks were run. No build, container, host installation, device change, Git staging/commit/push or publication was performed.

## Coordination interfaces

- The performance-owned `default/pi/build-environment.sh` must be sourceable without side effects and expose `omarchy_pi_prepare_build`. Entry points call it before their first `mktemp` or `makepkg`; it should export bounded Make/Cargo/CMake/Ninja flags, disk-backed `TMPDIR`, and cache locations while honoring explicit caller settings and checking space. Do not reset `HOME`.
- **Image factory change required:** its pre-installer `prepare_build_user` must establish Omarchy trust before its first sync against the new Pi template. Source `install/helpers/pacman.sh` and call `omarchy_pi_bootstrap_keyring` in the chroot (after arranging disk-backed `TMPDIR`), then populate `archlinuxarm`. That helper uses fixed reviewed SHA-512 digests for the public Omarchy keyring files. The factory may perform `-Syyuu` only on its disposable fresh rootfs. Existing rolling installations are deliberately refused by the updater; no automatic transition is supported.
- New profiles record `OMARCHY_RPI4_PACKAGE_POLICY=stable-4.5`, retain `OMARCHY_PACMAN_PROFILE=rpi4`, and use released stable ARM64 plus the ALARM stable closure. Legacy profiles must fail before source fetch, repo refresh or a package operation, with fresh-media/reflash guidance.
- The local settings package omits every generic mkinitcpio and Limine fragment, vendor `90-omarchy` zram, upstream oomd/zswap/USB-autosuspend policy, and `vm.*` reclaim tuning. Networking and file-watcher sysctls remain. Performance-owned `default/pi` policy remains authoritative; this owner does not edit those files.

The parent owns merge staging and consolidated native ARM Linux, package-build and image validation.

## Additional factory coordination

- Build helper integration now passes `--config "$OMARCHY_PI_MAKEPKG_CONF"` and collects exactly declared artifacts using `makepkg --packagelist` (the default destination is `$OMARCHY_PI_BUILD_CACHE/packages`), then persists them before helper cleanup. No routine application source builds remain.

The updater now validates `/boot/Image` and both firmware/Linux Pi 4 DTBs as well as the established rootfs boot checks. The factory audit should check these actual Linux assets too. Some assertions there encode the retired rolling policy, presence-only local recipe builds, or old updater sequencing and will need the parent's reconciliation against the new focused fixtures.

## Stable metadata findings during implementation

A fresh download of all four stable repository databases found 13,598 valid package records and one all-NUL unrelated `extra/findnewest-0.3-4/desc` record. The resolver warns about that incomplete entry; required requests still fail if they cannot resolve, and native libalpm must validate the transaction. Unlike the earlier rolling-mirror audit, **this stable Neovim package has no `Provides=nvim`**: the contract explicitly maps the upstream `nvim` spelling to the same `neovim` app. Stable has neither traditional `vi` nor a provider. `vi` is explicitly supplemental/optional; full mode reports its absence. Inspecting stable `vim-9.2.1178-1` confirmed that it does not ship `/usr/bin/vi`, so no false provider or silent replacement was introduced. Default Neovim remains required. Native solver, signatures, and ELF loading are still unverified.

The bootstrap helper now removes its unowned conventional public-key source files after populating pacman's local keyring, so the subsequent signed `omarchy-keyring` package can own those paths on direct installations as well as images. Already package-owned files are retained. The factory's additional ownership-aware cleanup remains harmless. Builder artifact collection now uses `makepkg --packagelist`, honoring explicit `PKGDEST` and copying only declared outputs into the persistent output directory; caller archives are never moved out of `PKGDEST`.

## Completed behavior

- `rpi4` remains a repository profile, not a new architecture/family. Its only supported package channel is released stable ARM64: Omarchy's stable aarch64 repository plus `arm-stable-mirror.omarchy.org/$arch/$repo`. Templates retain trusted required signatures and protect `omarchy`, `omarchy-settings`, and the upstream dev pair through `IgnorePkg`.
- Bootstrap public trust uses the three reviewed SHA-512 digests from the pinned keyring recipe over HTTPS before any sync. It never disables signatures, fetches an unverified keyserver key, or removes an installed keyring package's files.
- `install/omarchy-rpi4.packages` classifies the composed upstream base/ARM set as required unless explicitly optional/excluded; unknown new entries fail closed. It adds Pi boot/runtime packages, speedtest, rtkit, and the reviewed compositor/plugin/Quickshell pins. mise must be at least 2026.10.11. The resolver understands versioned/unversioned Provides and package-name mappings, asks pacman's solver for closure, rejects foreign architecture/protected-core dependencies, requests exact selected repository versions, and verifies installed versions rather than presence. Missing required runtime is fatal. Optional omissions and the selected plan are persisted under `/var/lib/omarchy/rpi4-package-{omissions,plan}` after success.
- `--minimal` omits only the explicit optional set. The required 4.5 migration applications, titlebars, Omasnap, OWE and power-daemon provider remain present. There are no routine local application source builds; only the four existing local core artifacts are constructed.
- The recipe pin is `c7a1ef7f86cccab072fb11f22564862c03f50199`; reviewed [core](https://github.com/omacom/omarchy-pkgs/blob/c7a1ef7f86cccab072fb11f22564862c03f50199/pkgbuilds/omarchy/PKGBUILD) and [settings](https://github.com/omacom/omarchy-pkgs/blob/c7a1ef7f86cccab072fb11f22564862c03f50199/pkgbuilds/omarchy-settings/PKGBUILD) both pin final release `ac2690cd7be4f47e4a255f5e2e78d904d436b068`. Explicit and cached recipe checkouts must be clean, from the expected origin, and at the reviewed commit.
- Core/settings use `4.5.0.pi4.1-1`, retain exact pairing and the released security-helper ownership/scriptlet contract, and omit the theme-intros hard dependency as a documented static-background policy. The staged runtime version matches the Pi identity. Font/keyring source checks remain active: no `--skipinteg`, `--skipchecksums` or `--skippgpcheck`. `--nodeps` applies only to constructing the mutually dependent core artifacts; the final installation checks dependencies normally.
- The Pi settings wrapper removes every live generic mkinitcpio/Limine fragment, vendor zram, upstream oomd/zswap and USB autosuspend policy, and conflicting upstream `vm.*` settings after the upstream recipe's runtime-profile checks. It retains networking/inotify sysctls, filters missing backup entries, and preserves settings ownership of sudo/security helpers and the grant-revocation hook. Performance-owned Pi defaults are applied normally afterward.
- A new `AbortOnFail` pacman hook blocks direct repository/local installation, upgrade, removal or dev-pair replacement of the local core unless the Pi installer/updater explicitly authorizes the complete checked artifact set. This protection also applies when a caller bypasses the ordinary direct-system-upgrade warning. `--packagelist` and `omarchy-pi-artifacts.list` select the completed build, leaving unrelated/stale caller archives untouched. All four expected package names, versions and architectures are checked before install; installed metadata is checked before advancing receipts.
- Fresh installation refuses an already-provisioned system before seeding user defaults or changing repositories. Whole-system `-Syyuu` alignment is limited to a fresh rootfs. New installed profiles declare `stable-4.5`; legacy rolling profiles are refused before new-updater source/repo/package mutations, with backup/spare-media/reflash guidance. An old packaged updater sourcing the new installer leaves also receives the refusal before recipe/package changes, although its earlier source fetch cannot be undone by these leaves. No rolling-to-stable transition is claimed.
- On stable systems, the outer updater prepares source, updates keyrings, performs the full coherent system/runtime transaction, then reconciles/rebuilds local core before migrations. Direct Pi core updates perform the same prerequisite sequence. Source origin/main/upstream/clean guards remain. Current-source receipts cannot hide stale installed versions; failed/incomplete artifacts or installation never advance the receipt. Core replacement uses the released Hyprland reload guard. Pi migrations wait for a successful current-shell restart; a locked/unavailable shell leaves them pending with retry guidance. AUR failures retain upstream failure propagation.
- Pi boot validation checks a mounted FAT `/boot`, 64MiB free, firmware/U-Boot, Linux Image, both Pi 4 DTB paths and the installed module tree, explicitly runs `mkinitcpio -P`, parses the resulting initramfs and verifies its module version, and parses the owner's existing Hyprland config as that owner. Any failure blocks update completion/reboot prompting. These are static checks, not proof of physical boot.
