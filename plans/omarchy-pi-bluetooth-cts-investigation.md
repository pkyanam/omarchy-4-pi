## Exact source contract

References below are relative to `bt-uart-progress-candidate/source/`.

- `drivers/tty/serial/serial_core.c:202` calls this operation `uart_change_line_settings()`, the current equivalent of older `uart_change_speed()` discussions. It calls the driver's set-termios first, then under the UART lock updates `UPSTAT_CTS_ENABLE` from CRTSCTS and recomputes `hw_stopped = uart_softcts_mode(port) && !(get_mctrl(port) & TIOCM_CTS)`. Changed state calls stop-TX or start. This path does not increment `icount.cts` or call `uart_handle_cts_change()`. Thus the observed state changes without CTS callbacks are consistent with termios re-evaluation; entry probes alone do not prove the call stack.
- `include/linux/serial_core.h:1165` enables software CTS only when CTS_ENABLE is set and AUTOCTS is clear. Setting AUTOCTS is a promise that the owning hardware/driver handles gating; it is not permission to ignore CTS.
- `drivers/tty/serial/8250/8250_port.c:1927` implements get-mctrl through `serial8250_modem_status()`, then converts MSR to TIOCM flags and optionally merges GPIO modem inputs. At `:1760`, modem-status invokes CTS-change only with delta status, MSI enable and initialized tty state. At `serial_core.c:3471`, the CTS handler increments its counter and starts/stops software flow. AUX cannot produce the normal DCTS/MSI contract, so a later ready level cannot necessarily resume this port.
- `8250_bcm2835aux.c` registers FIFO|MINI, fixed 16550 type, and emulated RS485 callbacks. It has no AUTOCTS status handling, custom set-termios, custom get-mctrl, CTS GPIO declaration, or NOMSI workaround. Its cached CNTL starts at RXEN|TXEN and is written by RS485 callbacks. The defines for AUTOCTS/AUTORTS alone enable nothing. Current hardware CNTL contents were not measured.
- Generic `serial8250_set_afe()` at `8250_port.c:2703` controls MCR AFE. AUX automatic flow is in CNTL instead; setting `UART_CAP_AFE` would program the wrong contract. Never add it as a shortcut. Never suppress CRTSCTS globally.

The [Broadcom/Raspberry Pi BCM2711 manual](https://datasheets.raspberrypi.com/bcm2711/bcm2711-peripherals.pdf), chapter 2, tables 6–13, documents only RX/TX interrupts, no CTS delta interrupt. MSR bit 4 inversely reflects CTS pin level; its low four bits are reserved. CNTL bit 3 gates TX, bit 7 selects CTS assertion polarity: set means active low. RXEN/TXEN are bits 0/1; RTS automatic control, threshold and polarity occupy bits 2/4–6. Hardware gating cannot make a permanently deasserted CTS ready. The manual also lacks framing/parity detection on AUX, so zero such counters is weak evidence. Chapter 5's ALT5 map identifies GPIO30=CTS1, GPIO31=RTS1, GPIO32=TXD1, GPIO33=RXD1. An after-power-off low GPIO30 therefore says nothing about powered readiness.

## Real history: fixes exist

Primary history and exact pinned driver copies are retained under `bt-cts-candidate/reference/`, with an SHA-256 manifest. These are reference material, not applied package inputs.

[Raspberry Pi commit 33d3645825ac76bf216b6fcb5cebb60954a13e7c](https://github.com/raspberrypi/linux/commit/33d3645825ac76bf216b6fcb5cebb60954a13e7c), committed 2026-04-20, describes transmission staying stopped if termios changes while CTS is high. It marks AUX `UART_BUG_NOMSI`, starts a timer on software stop, and synthesizes the CTS callback when a subsequent status read is ready. This is a genuine downstream recovery workaround; it is absent from the exact saved source. It changes generic 8250 timer/status code, requires lifecycle/timer review, and is not a narrow owning-driver hardware-flow patch. No polling backport is prepared here.

[Mainline commit ca576923c39863ac528427b563ea2f6631703d22](https://github.com/torvalds/linux/commit/ca576923c39863ac528427b563ea2f6631703d22), committed 2026-10-13, implements AUX hardware RTS/CTS using `uart-has-rtscts`/UPF_HARD_FLOW, AUTOCTS/AUTORTS status, active-low CNTL masks, RTS mctrl gating, throttling and RS485 exclusion/recovery. This is merged upstream, superseding the August proposal. It is absent from the exact saved 7.3 source despite the newer mainline history; never substitute branch-tip source for the recorded archive. The later mainline commit `d6a0791098bedea41e813db646d21c9ba30004ec` changes 8250 operation types, so copying today's entire driver onto the saved kernel is inappropriate. The pinned Raspberry Pi rpi-6.18.y file still uses NOMSI rather than that AUTOCTS implementation at the inspected history tip.

Prefer reviewing this existing upstream change against the exact kernel over inventing a new solution. Its fallback strips CRTSCTS when neither hardware flow nor a CTS GPIO can work; applying it without a reviewed DT property would change this board's behavior. No property, capability or patch is activated here. An eventual inactive backport must test the actual production functions, including termios transitions, active-low CNTL masking and RXEN/TXEN preservation, manual RTS clear/set/B0, throttling, RS485 on/off and RX restoration, startup/resume reprogramming, and unconfigured/CTS-GPIO ports. Host mocks cannot qualify pins, locking or resume hardware.

## Concrete next unit: parent-only bounded combined capture

`tools/pi-experiments/bluetooth-cts-snapshot.py` defaults to an offline plan. Explicit `--observe-actions` reads only fixed GPIO/pinctrl/procfs files and the existing UART collector's actions JSON; it writes one fresh private disk-backed JSONL file. It never registers probes, changes flow, acquires GPIO lines, accesses UART registers, binds devices or starts the trace. GPIO text is private evidence and can include unrelated line labels. Every read is bracketed by monotonic timestamps, and samples follow a fixed finite schedule through 11 seconds after trace-start. It stops on a measured read taking over 50 ms. A blocking debugfs read can defeat that check until return; use the external deadline and stop on an unresolved process, without another attempt.

Parent procedure, not executed here:

1. Reserve sole Pi access, healthy display/storage and no concurrent benchmark/trace or build transaction. Verify current boot line identity/BTF and unchanged hashes of the three existing trace helpers. Reuse only parent-reviewed UART installed formats for this exact boot/contract; if anything changed, do disabled validation first and review fresh formats. Retain current DT and GPIO-controller labels before interpreting pin routing. Require debugfs pinctrl `pins`, `pinmux-pins` and `gpio` already available; do not mount or alter a controller for this observer.
2. Choose a fresh private disk-backed directory (mode 0700). The future UART output directory and its `actions.json` must not exist. Start the observer under the parent's root procedure: `timeout --signal=TERM --kill-after=1s 45s python3 bluetooth-cts-snapshot.py --observe-actions /var/tmp/CTS_UNIT/uart/actions.json --output /var/tmp/CTS_UNIT/gpio.jsonl`, redirecting complete stdout/stderr to a private log. Retain its exact PID. Wait for the JSONL `armed` record and inspect it; do not infer readiness from a process merely existing. The observer waits at most 30 seconds for trace-start.
3. Immediately invoke the unchanged UART helper once with the proven identity, reviewed formats hash and `/var/tmp/CTS_UNIT/uart` as output, using the existing guarded 12-second execute command. The observer timestamps on the same CLOCK_MONOTONIC as `actions.json` and the instance mono trace clock; verify that clock in `instance.json`. The bounded 10 ms actions-file wait is diagnostic coordination only, not a deployed background poller. Do not combine any second tracer or independently rebind. No local variables need interpolation into a remote shell snippet.
4. Retain both complete logs and observer exit status. On any failure, stop only the observer PID if still alive and let the existing tracer's own cleanup finish; never kill an unrelated process, change shared policy or automatically retry a bind. Confirm no unresolved workers and exact state/binding/taint restoration. Keep partial evidence and refusal output. A missed schedule, slow read, no powered sample or incomplete GPIO record remains an unknown, not permission to retry repeatedly.
5. Correlate each pin read's interval with the UART events and each GPIO BT_ON read's interval. These files are sequential reads, not an atomic snapshot: a sample that spans power-down cannot establish a powered CTS level. Treat only clearly bracketed, stable powered intervals as supportive. Reject absence claims with any probe miss/drop/truncation or missing observer records. GPIO samples are sparse and may miss transitions; they cannot prove continuous state or physical TX. Debug GPIO reads may perturb timing, particularly through the firmware mailbox.

If powered samples show GPIO30 high at software stop and subsequently low with no CTS callback/TX progress, the missing-MSI recovery explanation gains direct support. Review the upstream AUTOCTS implementation and actual DT opt-in as a coherent inactive candidate next. If GPIO30 stays high while BT_ON is requested high, automatic flow would also wait: investigate controller power/reset/readiness and routing first. If observer latency misses the brief powered interval, stop at that limit; parent-coordinated electrical capture of CTS/RTS/TX/RX/BT_ON or a reviewed matching-driver diagnostic is the next discriminating unit. No userspace UART register/devmem access or writes are permitted. No working-radio claim follows from any of these software observations.
