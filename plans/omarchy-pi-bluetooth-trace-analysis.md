## Exact Linux flow and UART state

Reference is the checksum-identified `linux-7.3` archive and `/tmp/omarchy-bt-73-source`, upstream commit `c03c1a14507dfaf8b856c2608f9ac216021fc222`. The new candidate manifest pins its two input hashes. Additional selectively extracted files are retained in the candidate's `reference/linux-7.3/`; no whole kernel was extracted or built.

1. `bcm_serdev_probe()` obtains GPIOs with `GPIOD_OUT_LOW`, reads the DT operational speed, and calls `bcm_gpio_set_power(false)` before registration. The saved compatible `brcm,bcm43438-bt` selects `drive_rts_on_open=true`, with no early-baud suppression. `bcm_gpio_set_shutdown()` writes the logical shutdown value equal to `powered`; a separately supplied reset GPIO would get its inverse. The saved DT describes shutdown, not a separate reset line.
2. Registration opens serdev before `bcm_open()`. `bcm_open()` temporarily calls `hci_uart_set_flow_control(true)`, requests power on, waits 100–120 ms through `bcm_gpio_set_power()`, then calls `hci_uart_set_flow_control(false)`. The helper's boolean is easy to misread: on serdev, true disables CRTSCTS and clears RTS; false restores CRTSCTS and asserts RTS. These are requests through tty operations, not measured pin levels.
3. `hci_uart_setup()` sets host initial speed to protocol default 115200, then sends the controller's requested 230400 using `bcm_set_baudrate()`. Only a successful command causes the host operational-speed call. The trace follows the error branch, so this path never requests host 230400. A failure is logged but current code continues into `bcm_setup()`.
4. `bcm_setup()` calls `btbcm_initialize()`, whose first operation is `btbcm_reset()`. A reset error returns before controller-version discovery and patchram selection/download. Missing `.hcd` files are therefore not established as this failure's cause.
5. `hci_cmd_timeout()` logs the opcode in `req_skb`, cancels the synchronous wait, restores command credit and schedules command work. `hci_cmd_sync_cancel_sync()` wakes the waiter without clearing `HCI_CMD_PENDING`. The next `hci_send_cmd_sync()` updates `sent_cmd` and sends Reset, but updates `req_skb` only when that pending flag was previously clear. This explains how the second timer can still print `0xfc18` while the reset caller fails. It does not prove a second vendor command was sent; btmon shows one vendor command and one Reset. Do not patch shared timeout state from this trace alone.

Source references: [Broadcom driver](https://github.com/torvalds/linux/blob/c03c1a14507dfaf8b856c2608f9ac216021fc222/drivers/bluetooth/hci_bcm.c), [HCI serdev](https://github.com/torvalds/linux/blob/c03c1a14507dfaf8b856c2608f9ac216021fc222/drivers/bluetooth/hci_serdev.c), [flow-control helper](https://github.com/torvalds/linux/blob/c03c1a14507dfaf8b856c2608f9ac216021fc222/drivers/bluetooth/hci_ldisc.c), [controller initialization](https://github.com/torvalds/linux/blob/c03c1a14507dfaf8b856c2608f9ac216021fc222/drivers/bluetooth/btbcm.c), [command worker/timer](https://github.com/torvalds/linux/blob/c03c1a14507dfaf8b856c2608f9ac216021fc222/net/bluetooth/hci_core.c), [synchronous request cancellation](https://github.com/torvalds/linux/blob/c03c1a14507dfaf8b856c2608f9ac216021fc222/net/bluetooth/hci_sync.c).

The exact AUX driver sets `UART_CAP_FIFO | UART_CAP_MINI`, doubles `uartclk` to account for divide-by-8 hardware, and inherits generic 8250 termios/divisor handling. It does not consume parent `skip-init`. Its source explicitly says automatic RTS is unsupported. That does not mean no flow control exists: tty CRTSCTS and generic software CTS handling remain relevant. There is no basis to force `UART_CAP_AFE` or enable hardware bits blindly.

An important unresolved handoff detail: AUX `CNTL` is cached as RXEN|TXEN in the probe's private state, but that assignment is not itself a hardware write; this file writes the cached value in its RS485 callbacks. Thus neither `skip-init` nor the software cache proves current RX/TX/auto-CTS/auto-RTS register state. No register readback was captured. Similarly, the tty serdev baud setter returns its local termios rate, not a physical baud measurement. A stable-looking 499999998 Hz clock snapshot cannot establish clock stability throughout initialization. [AUX source](https://github.com/torvalds/linux/blob/c03c1a14507dfaf8b856c2608f9ac216021fc222/drivers/tty/serial/8250/8250_bcm2835aux.c), [8250 implementation](https://github.com/torvalds/linux/blob/c03c1a14507dfaf8b856c2608f9ac216021fc222/drivers/tty/serial/8250/8250_port.c), [tty serdev adapter](https://github.com/torvalds/linux/blob/c03c1a14507dfaf8b856c2608f9ac216021fc222/drivers/tty/serdev/serdev-ttyport.c).

## Firmware lineage resolved by region, not whole-file equality

The parent's copied mounted-card file `optimization/current-RPI_EFI.fd` hashes to `9d7e2b14292e9275f1bc00ebcb07fc879a629c343cedea6381776d1696d77067`. Local stock `firmware/pftf-v1.53/RPI_EFI.fd` hashes to `8334d9d3c3fe5341fb9876f2ddf653eca7b260ee2cda669c5446a0dd7f0104c5`. They are **not identical files**. Both are 3,997,696 bytes (`0x3d0000`). Other earlier local firmware copies have other hashes and must not stand in for this capture.

The [PFTF v1.53 tree](https://github.com/pftf/RPi4/tree/v1.53) pins edk2-platforms `c8295e076affae5cf04fd4234db13a0e025f44e1`, edk2 `2970e5699ba6267f3384ffab20f96647578aebc8`, and edk2-non-osi `7ac12d81e02b323bffdf1ef3c188ea33c2185c91`. Its operative [RPi4.fdf](https://github.com/tianocore/edk2-platforms/blob/c8295e076affae5cf04fd4234db13a0e025f44e1/Platform/RaspberryPi/RPi4/RPi4.fdf) declarations locate the following regions. The nearby `0x001e...` comments are stale; use the actual `0x003b...` declarations. FD size is declared `0x3e0000`; these distributed binaries end at the last emitted region, `0x3d0000`.

| File offsets, end exclusive | FDF region | Changed bytes |
| --- | --- | --- |
| `0x000000–0x020000` | ATF | 0 |
| `0x020000–0x3b0000` | UEFI `FVMAIN_COMPACT` | 0 |
| `0x3b0000–0x3be000` | NV variable store | 24,802 |
| `0x3be000–0x3bf000` | NV event log | 0 |
| `0x3bf000–0x3c0000` | FTW working | 0 |
| `0x3c0000–0x3d0000` | FTW spare | 0 |

Independent offline comparison confines all differences to `0x3b0064–0x3b61fb`, inside the variable store. ATF region SHA-256 is `c35ec9d27dbf90dffbfda9167a6f957fc8394792c5061ca6d132cc53f405ceaf` in both; compressed UEFI region SHA-256 is `58f59562d1dad08a2d44d8357b024da8843c694972a306bf75b982a9be5b48cc` in both. There is **no executable-region divergence in these two files**. This is stronger than guessing from the version label and narrower than saying current firmware is stock-identical.

The pinned [VarBlockServiceDxe](https://github.com/tianocore/edk2-platforms/blob/c8295e076affae5cf04fd4234db13a0e025f44e1/Platform/RaspberryPi/Drivers/VarBlockServiceDxe/VarBlockServiceDxe.c) writes the mapped variable FV back through `FileWrite` at its offset, providing a source-supported mechanism for mutable on-card state. The changed region is therefore attributable to variable-store contents by layout; which settings/history produced those bytes was not decoded. Do not overwrite it with stock bytes or reset NVRAM. Byte equality of the code regions does not establish identical runtime settings, loaded image selection, VideoCore firmware, DTB or overlays.

The [v1.53 build workflow](https://github.com/pftf/RPi4/blob/v1.53/.github/workflows/linux_edk2.yml) pins the packaged DTB to Raspberry Pi firmware commit `b49983637106e5fb33e2ae60d8c15a53187541e4`, while fetching `start4.elf` and overlays from then-current master. A tag alone is not a complete binary manifest. Pinned [FdtDxe](https://github.com/tianocore/edk2-platforms/blob/c8295e076affae5cf04fd4234db13a0e025f44e1/Platform/RaspberryPi/Drivers/FdtDxe/FdtDxe.c) copies the firmware-provided FDT and makes memory/PSCI/framebuffer/Ethernet/USB/PCIe fixups; it contains no Bluetooth baud/reset fixup. Pinned [DualSerialPortLib](https://github.com/tianocore/edk2-platforms/blob/c8295e076affae5cf04fd4234db13a0e025f44e1/Platform/RaspberryPi/Library/DualSerialPortLib/DualSerialPortLib.c) detects console routing from GPIO14/15 mux and can initialize the selected UART; it is not evidence of Bluetooth initialization. The ACPI `Uart.asl` Bluetooth resources specify 115200, but this board uses DT and those ACPI resources do not control its serdev configuration. Preserve the distinction between console selection, Bluetooth routing and controller baud.

## Bounded candidate and completed checks

`bt-next-candidate/0001-bluetooth-transport-diagnostics.patch` adds dynamic-debug records for initial/operational host requested and reported speed, serial write requested/accepted lengths, received byte counts, and power request/delay completion. It keeps current setup order, return values, timing delays and error continuation. It does not include or alter the previous inactive fail-fast patch. It reads no UART registers, logs no payload/address/firmware-variable contents, and adds no polling. Logging can perturb timing and must be enabled for only the bounded diagnostic window.

`source/` holds the two candidate C files; `source-manifest.json` pins pristine and candidate hashes. `validate.py` applies the patch with fuzz zero to the pinned source in a temporary directory and compiles the entire actual `hci_uart_setup()` function with host interface stand-ins. Base and candidate both pass failure-continuation, success, zero-operational-speed and speed-precedence assertions. This checks preservation of setup control flow, not the UART/controller, all changed C functions, the complete kernel or module ABI. Initial harness attempts failed because the logging stand-in discarded arguments, then because it was unused in the base; those logs are retained and the stand-in was corrected. Final output is `validation.log`. No kernel/module/firmware build was run.

`compare-firmware.py` reproduces the region comparison without printing variable data; results are `firmware-regions.json`. Pinned primary source copies are in `reference/edk2-platforms/`. The candidate remains offline and outside all package source lists. No DT candidate is justified yet: lowering max-speed still issues an early vendor command, while routing changes, compatibility changes and reset-delay guesses confound the unresolved transport fault.

## Safe next diagnostic plan — parent only, not executed

1. First inspect the existing btsnoop and correlate monotonic timestamps; that capture already answers command ordering. Preserve current full firmware hashes/config, current DT, module provenance, taint, existing debug policy and driver ownership. Resolve UART console/getty/userspace-attach ownership from saved/current state before another trace. Retain encrypted recovery and the working DMA overlay.
2. Prefer existing scoped tracepoints or supported function tracing on the matching installed kernel before building anything. Check availability and event formats first. Use an isolated tracing instance, not global tracing state; reject unavailable probes rather than guessing addresses or argument layouts. Bound to one parent-coordinated rebind and roughly 12 seconds. Trace power/RTS requests, host termios, serial write acceptance, TX progress and RX/error counters. Enable HCI command-worker/sync debug only for the same window to distinguish `sent_cmd` from stale `req_skb`. Capture btmon concurrently. Do not start scans or pair devices during this window.
3. If existing tracing cannot expose the missing boundaries, review the logging patch and later integrate/build a matching kernel and headers through the owning recipe with a new release and bounded resources. That is a separate parent decision; this lane neither builds nor stages it. No standalone replacement module or forced capability is proposed.
4. For hardware state, use a reviewed driver-context snapshot under the port lock, at defined probe/open/termios points, if still necessary. Capture AUX CNTL RXEN/TXEN/autoCTS/autoRTS, divisor with DLAB restored, mux, and non-destructive status. Do not use userspace `devmem`, read RX data, write bits, or repeatedly sample clear-on-read status behind the driver. A logic analyzer observing TX/RX/RTS/CTS and BT_ON would distinguish electrical transmission/reset from software acceptance; voltage/pin access requires the parent's hardware coordination.
5. Cleanup must run on every exit: stop only the collector's own PIDs, restore the exact prior debug/trace policy, remove its own probes/instance, restore original binding, and capture post-state/taint. Never silently rebind repeatedly. Stop on storage/display/health regressions. Kernel taint zero and restored binding alone do not qualify Bluetooth.
6. Interpret one boundary at a time: zero/partial serial acceptance suggests queued transport/wakeup; accepted bytes with no TX progress suggests UART/CTS state; TX with no response suggests controller reset/clock/routing/receive path; RX errors suggest baud/electrical/clock trouble. An actual valid completion at 115200 is the prerequisite for diagnosing a later baud transition. Only then consider a narrowly evidenced upstream reset/baud-order/DT correction. Retest normal peripherals, coexistence and boot/resume separately after a real fix.

Remaining unknowns are physical UART rates and signals, live register state, in-window clock stability, electrical reset/power timing, RX errors, the effective full firmware/DT/overlay lineage, and actual controller identity/version. No working Bluetooth or performance result is claimed.
