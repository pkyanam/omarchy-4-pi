## Exact identity and source-backed boundary

`reference/RPi4.fdf` and `VarBlockServiceDxe.c` are fresh copies of the already pinned local primary sources from `bt-next-candidate/reference/edk2-platforms/`, whose trace-analysis report binds them to PFTF v1.53, edk2-platforms `c8295e076affae5cf04fd4234db13a0e025f44e1`, edk2 `2970e5699ba6267f3384ffab20f96647578aebc8`. No network source substitution was used. The manifest includes source hashes and pins; `generate.py` reproduces the proof from the actual source serialization and authenticated old capture. This uses the FDF's explicit definitions of both headers, rather than a separately downloaded C header or inference from the first changed byte.

The operative FDF declares NV_VARIABLE_STORE `[0x3b0000,0x3be000)`. Its DATA block explicitly serializes EFI_FIRMWARE_VOLUME_HEADER followed by VARIABLE_STORE_HEADER. Removing comments and decoding those literal source bytes yields exactly 100 bytes, retained as `reference/header.bin`, byte-identical to the authenticated old capture. FV HeaderLength is read from the actual field at offset48: `0x48`. Its block map is two eight-byte entries, including the terminator. The following store header explicitly contains GUID16 + UINT32 Size + UINT8 Format + UINT8 State + UINT16 Reserved + UINT32 Reserved1, totaling28 bytes. Therefore the source-derived data boundary is `0x3b0000 + 0x48 + 28 = 0x3b0064`. No observed difference offset is an input to that calculation.

Exact required EFI size is `0x3d0000` (3997696 bytes), the distributed file length; the FDF's declared FD capacity `0x3e0000` is not accepted as an alternative file length. Only `[0x3b0064,0x3be000)` is mutable variable data. This is identity validation, not validation of individual variable-record semantics or runtime settings. It does not authorize writes to that range.
