## Findings and fixes

The original helper accepted symlinks in the media configuration's parent path, in overlay parent paths within the mounted tree, and in an existing backup pointing to the exact baseline bytes. It synced file contents but did not sync the overlay directory before publishing config. Caught partial-write/fsync/rename failures left owned temporary files and prevented retry. Package removal had no guard requiring firmware restore.

`firmware/media-sync.py` now rejects those symlink paths, checks backup directory ownership/permissions, serializes cooperating writers with a root-state lock, syncs each renamed file's parent directory, verifies published overlay bytes before config publication, and cleans up only temporary files created by that invocation on caught failures. A pre-existing temporary file still fails closed for operator review. The helper's new read-only `remove-check` requires baseline config and absence of the owned overlay. `firmware/09-omarchy-pi4-cts-remove.hook` invokes it before removal with AbortOnFail; `firmware/PKGBUILD` installs that hook and contains matching source hashes. Only corresponding firmware entries in `INPUTS.sha256` were refreshed, plus the new hook entry. No kernel recipe or DT payload changes.

Apply writes overlay before config; restore writes and syncs baseline config before deleting only `overlays/omarchy-pi4-aux-rtscts.dtbo`. Restore rejects a foreign replacement overlay instead of deleting it. Whole fixture manifests verify all other firmware bytes, including DMA and EFI sentinel files, remain unchanged across repeat/apply/restore. Config bytes are the actual saved baseline/candidate inputs; unrelated firmware bytes and overlay bytes in the fixtures are explicitly synthetic.

Failure injection proves old config bytes survive partial temporary-file writes, file fsync failures and rename failures before config publication, including overlay-directory fsync failure. Retry succeeds after caught failures. Restore failures before config rename preserve the active config/overlay pair. A failure syncing the config directory AFTER its rename leaves the new config visible in this filesystem fixture. It is an error and stop/no-reboot state, not an automatic rollback guarantee. The test verifies that distinction and subsequent explicit restore. Sudden process death/power loss can leave temporary files, requiring review; no crash-durability claim is made.

## Physical FAT, immutable baseline and release limits

No real FAT device/mount is available within the authorized no-device/no-mount fixture. vfat, UUID and mount identity are mocked; the actual filesystem is Docker's writable container filesystem. This establishes helper control flow and observed file I/O only. It does not establish FAT rename/fsync/power-loss durability, hardware write-cache behavior, final firmware DT application, radio operation, package signatures/archive acceptance, actual kernel/headers/UKI compatibility, or target ALPM ordering with all installed hooks. Real archive preflight, identified-card transaction and physical boot/FDT/radio/rollback verification remain parent gates. A successful pacman exit alone cannot release the no-reboot stop.

`RPI_EFI.fd` includes mutable firmware-variable state. The exact full-file hash is deliberately retained as a private fail-closed baseline: legitimate NVRAM changes can reject check/apply/restore/removal. This is not an immutable-code identity and is not suitable evidence of a normal public update mechanism. Public update support needs an explicitly reviewed design separating executable identity from variable state and preserving legitimate variables, plus lifecycle/cross-version testing. Do not broaden hashes or overwrite firmware variables to make a check pass. Baseline drift during recovery needs parent reconciliation against saved media and archives.

The first-install extracted-archive check remains necessary because a new package cannot supply its own pretransaction hook for that transaction. Any post-hook error requires inspection/rollback and no reboot, even when pacman returns zero. Removal now requires explicit successful restore before `pacman -R`; exact dependency still requires companion removal before downgrading the matching kernel/headers set. No dependency bypass is proposed. Full firmware/ESP archives remain separate from root snapshots and the helper's supplemental file backup.

The parent's `results/pi4-4gb-native/2026-11-08/recovery/README.md` and `restore-native-sanitized.log` demonstrate an actual native **same-version** root snapshot restore followed by reboot: active writable @ ID270, marker absent, installed kernel/headers 7.3-32.1 and unchanged UKI hash. Therefore older “recovery not demonstrated” wording must not become a new permission gate for that completed rehearsal. It does not prove 32.2 → 32.1 kernel/DT/firmware rollback, reconstruction of a wiped ESP, or full media-loss recovery. Cross-version kernel/DT rollback and physical CTS firmware acceptance remain future gates.
