## Decision and evidence boundary

Use the existing native Vulkan loader and Mesa V3DV through a small C11 client. A GLSL shader compiled ahead of time to SPIR-V performs an integer grayscale 3×3 box filter in storage buffers. This is a capability/correctness exercise for BCM2711's V3D 4.2 and Mesa 26.2.6, separate from rendering, display import, fixed-function codec decode and Vulkan Video. It proves none of their performance. It is not an OpenCL test, desktop acceleration claim, Pi OS comparison or energy result.

The provided target is a 4GB Pi 4 with vulkan-broadcom/Mesa 26.2.6 and kernel 7.3-32.1. Those are inherited board/package facts, not live measurements by this lane. The harness refuses CPU/software devices and a nonmatching V3DV/Mesa identity. A reported driver string is runtime identification, not cryptographic installed-package provenance; parent must retain package versions, source/build IDs and loaded library/ICD hashes separately.

- [Mesa 26.2.6 v3dv_queue.c](https://gitlab.freedesktop.org/mesa/mesa/-/blob/mesa-26.2.6/src/broadcom/vulkan/v3dv_queue.c), SHA-256 `7a3768a22f5d87fcde667bf4a0fa326bd5fb0f9c1fa7ffc790d9450a2d4bbd1d`, `handle_timestamp_query_cpu_job`, submits `DRM_V3D_EXT_ID_CPU_TIMESTAMP_QUERY` via the kernel CPU queue and serializes prior work. [v3dv_query.c](https://gitlab.freedesktop.org/mesa/mesa/-/blob/mesa-26.2.6/src/broadcom/vulkan/v3dv_query.c), SHA-256 `7f2ef8206304495f997997cf699dab1d78d90b9b5679ca82eb7dd09da9106203`, manages timestamp storage/results. These two files were downloaded directly from official GitLab in this lane. Timestamp support is not evidence of a pure shader-cycle counter. This candidate deliberately omits queries and reports `gpu_execution_ns=unknown`.
- [Khronos dispatch contract](https://docs.vulkan.org/refpages/latest/refpages/source/vkCmdDispatch.html): dispatch counts are workgroups. The client checks queried per-axis workgroup size/count, invocation count, two storage-buffer descriptors, storage range and 8-byte push constants before creating resources. Local size is 8×8×1, largest dispatch 33×25×1; shared memory and optional features are unused.
- [Khronos synchronization contract](https://docs.vulkan.org/spec/latest/chapters/synchronization.html): the client requires host-visible coherent buffer memory, writes it before submission, records host-write to compute-read/write and compute-write to host-read barriers, then waits for the fence before reading/reusing/freeing memory. Coherent memory removes explicit cache flush/invalidate calls, not synchronization requirements. Lack of such memory is an explicit unsupported prerequisite, not a reason to skip synchronization.
- [Khronos fence contract](https://docs.vulkan.org/refpages/latest/refpages/source/vkWaitForFences.html): the two-second wait can be adjusted by implementation timeout accuracy. It cannot cancel submitted GPU work. A process watchdog bounds userspace waiting, not kernel recovery.

Source files and hashes are retained under the candidate directory. These contracts establish a plausible portable implementation path; only compilation and actual parent execution can qualify the candidate on the installed stack.

## Kernel, reference and bounds

The shader reads one uint32 per grayscale pixel, each in [0,255], sums the clamped 3×3 neighborhood and writes `floor(sum/9)` to a separate uint32 buffer. Sum is at most 2295; no floating-point tolerance, overflow, image format, texture sampler, atomics, subgroup, shared-memory or optional shader feature is involved. Storage buffers represent the image and exercise compute without allocating a surface or connecting to Wayland/X11.

Exactly three submissions occur: 1×1 constant255, 17×19 corner impulse255, and 257×193 deterministic mixed input. Each submission has one dispatch and no repeat/warmup loop. The odd dimensions exercise masked excess invocations. The impulse's first two rows begin [113,56,0,…] and [56,28,0,…]; the 1×1 result is 255. An independent scalar C traversal computes the reference from the actual input. Every output pixel is compared exactly; the entire input is checked unchanged and every unused output word is checked against a sentinel, including 64 trailing guard words. These checks catch incomplete writes, wrong borders, wrong division, stride mistakes and writes beyond the logical shape within the allocated range. They are not a general memory-safety proof.

Largest image is 49,601 pixels; two buffers are 198,660 bytes each including guards. Each driver allocation is independently capped at 4MiB (alignment overhead included); there are exactly two allocations. Shader file size is capped at 64KiB. Physical-device and queue inventories are bounded. Mesa/loader/compiler internal allocations are outside the two-buffer bound. There is no performance scaling CLI or arbitrary dimensions/count option.

Parent first schedules an exclusive short Pi slot, checks normal desktop health and existing render-device access through normal session permissions, records the exact kernel, vulkan-broadcom/Mesa and loader versions and ICD/library paths/hashes, cooling/throttle state and workload/session context. After parent supplies the compiled native files on the Pi, under the normal user:

```bash

python3 tools/pi-experiments/gpu-compute-run.py --binary /path/gpu-compute-vulkan --device-uuid UUID_FROM_INVENTORY --shader /path/box.spv --output /path/new-compute-result
```

The UUID must be the exact 32-character lowercase value printed by inventory. Selection also requires the Mesa V3DV driver ID/name, `Mesa 26.2.6` version boundary, a `V3D 4.2` device name and a non-CPU device. Enumeration-index changes cannot silently select another GPU; absent or duplicate matching UUID fails. Do not change these checks to make a different device pass.

The runner refuses root, uses new output directories, records executable/shader hashes, selected environment overrides and UTC invocation time, preserves complete stdout/stderr and writes result metadata. The client has a 12-second process alarm and two-second fence deadline per submission; the supervisor has a 15-second wall deadline and kills its process group without a second blocking wait. No automatic retry occurs. A killed process does not guarantee immediate cancellation of kernel/GPU work. On a fence/submit failure, the client exits without destroying potentially pending Vulkan resources; process/driver teardown owns them. Ordinary success and pre-submit failures destroy every created object in dependency order. No unbounded `vkDeviceWaitIdle` is used.

For any timeout, device loss, validation/correctness error, runner failure, new desktop fault or abnormal health signal: stop the experiment, retain logs, and hand control to the parent. Parent checks desktop responsiveness and existing accessible kernel/driver diagnostics for V3D faults/reset/OOM, temperature/throttle and memory pressure using its existing policy. Do not request privileges, retry dispatch, reset devices, restart services or reboot automatically. Parent decides recovery. A parent/operator interrupt should likewise end the slot and trigger health review.

## Measurements and acceptance

Each case logs shape/pattern, pixels, nine logical input reads and one output write per pixel, scalar reference wall/process-CPU ns, and host submit-to-fence wall/process-CPU ns. Logical accesses are algorithmic counts, not physical DRAM bytes or hardware counters. Submit-to-fence includes queueing, driver submission, scheduling, execution and completion; it excludes pipeline setup, input initialization, command recording and output checking. Process CPU excludes kernel worker CPU and unrelated system work. Setup wall time is logged separately. No GPU-versus-CPU speedup is computed from these scopes. Pure GPU execution and energy remain unknown.

Accept only if the named target/driver checks pass, all three cases have zero mismatches/corruption, the terminal `correctness=PASS` appears, exit code is zero, and parent post-run health is unchanged. Missing API/limits/host-coherent memory/toolchain is an explicit unsupported/blocked prerequisite, not a pass. A timeout or mismatch is a failed experiment even if partial cases passed. Compilation/linking and SPIR-V validation succeeded. Runtime correctness, timing gain, power benefit, codec support, desktop acceleration and Pi OS parity remain unmeasured.
