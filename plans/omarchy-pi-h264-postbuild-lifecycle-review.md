## Smallest actionable finding: debugfs retains unowned module operations

`vc_sm.c:261–266`, `vc_sm_cma_debug_fs_fops`, has open/read/llseek/release callbacks but no `.owner`. Contrast the misc fops at `1564–1572`, which already set `.owner = THIS_MODULE`. `vc_sm_connected_init:1587–1594` publishes `/sys/kernel/debug/vcsm-cma/state` with this unowned operations table through ordinary `debugfs_create_file`. `vc_sm_cma_single_open:256–259` uses `single_open` without replacing the proxy file operations. An ordinary debugfs open therefore takes the full-proxy path.

The exact kernel's `fs/debugfs/file.c:434–480`, `full_proxy_open_regular`, obtains `fsd->real_fops`, calls `fops_get(real_fops)` at line 451, then calls the real open. The target `include/linux/fs.h:2351–2360` defines `fops_get`/`fops_put` in terms of the real operations table's `owner`. A NULL owner does not retain VCSM. The core debugfs proxy file itself is insufficient to retain the module containing the real table.

`bcm2835_vc_sm_cma_remove:1717–1724` removes debugfs before stopping SMIO. Removal protects active normal reads, but it does not require every already-open debugfs fd to close. Crucially, kernel `full_proxy_release:415–431` deliberately runs after removal: it reads `fsd->real_fops`, dereferences `real_fops->release`, invokes it, and calls `fops_put(real_fops)`. The operations table lives in VCSM module storage. Even though this table's release target is the core `single_release`, accessing that target still dereferences the module's table.

Concrete schedule with no imported buffers and a responsive peer:

1. Open the debugfs state file and retain its fd; no misc fd or dma-buf is required.
2. Ordinary VCSM module unload has no reference from that debugfs open. Its synchronous remove may remove debugfs, stop/join SMIO, and return.
3. After module reclamation, close the old debugfs fd. `full_proxy_release` accesses the stale real operations table.

This is a source-established missing lifetime reference; no forced unload, missing firmware acknowledgement, or DMA-quiescence inference is needed. Whether a particular runtime reaches the schedule is untested. Earlier documents listed broad “debugfs admission” uncertainty; they did not identify this precise operations-table lifetime defect. This review makes that existing review category concrete.

### Narrow implementation and acceptance

Add `.owner = THIS_MODULE` to `vc_sm_cma_debug_fs_fops` only. Use the existing debugfs proxy's successful-open/final-release reference pairing; introduce no asynchronous self-pin or permanent module reference. Keep `single_release` as the release operation because it does not dereference the retired `sm_pde_t`/device state. Do not mix this unit with generation redesign, firmware capability negotiation, or ioctl cleanup.

Source acceptance must verify the real table reaches `debugfs_create_file`, successful proxy open retains its owner, failed open balances that reference, and final proxy release drops it after `single_release`. Ordinary read/seek proxy protection and removal ordering must remain intact. A grep asserting the new initializer would only detect edits to itself and earns no new test.

Behavioral acceptance, when separately authorized and safe for the parent: on the exact kernel/modules with no outstanding buffers, retain an open debugfs state fd and attempt ordinary, non-forced VCSM unload; it must refuse while that reference exists. Close the fd and verify its reference is released and a later ordinary unload can proceed under the existing cooperative service-close prerequisites. Also cover a failed debugfs open without a reference leak. Removal/unbind while a debugfs fd remains open must suppress subsequent state access and allow final `single_release` safely while the module remains retained. These are real kernel debugfs/module-lifetime checks, not a stub that supplies the pin itself. They were not run here and do not authorize loading this candidate. Rebuild only under parent authority; compilation would not establish this behavior or full safety.

## Separate newly identified blocker: installed fd loses its reference on copyout failure

The userspace `VC_SM_CMA_CMD_IMPORT_DMABUF` branch in `vc_sm_cma_ioctl_admitted:1468–1502` obtains a newly exported dma-buf from `vc_sm_cma_import_dmabuf_internal:971–982`. It calls `dma_buf_fd(new_dmabuf, O_CLOEXEC)` at `1491–1492`, then reads `buf->vc_handle` and `buf->dma_addr`, and combines fd failure with `copy_to_user` failure at `1496–1501`. Both failures call `dma_buf_put(new_dmabuf)`.

Exact kernel `drivers/dma-buf/dma-buf.c:788–804` shows that successful `dma_buf_fd` installs `dmabuf->file` using `fd_install` without acquiring an additional reference. `dma_buf_put:867–874` calls `fput`. Thus successful fd installation followed by copyout failure drops the reference transferred to the fd table, leaving the installed descriptor without its required file reference. This can release the dma-buf file while the fd still points at it. The imported mapping's later RELEASED retention does not retain that file object. Separately, another thread sharing the fd table can close the newly installed fd before the field reads; internal import has already called `vc_sm_import_finish`, so the outer branch lacks the allocation helper's setup protection.

The ALLOC ioctl has the related leak direction: `vc_sm_cma_ioctl_alloc:1377–1395` installs the fd, and outer copyout failure at `1456–1464` returns `-EFAULT` without removing or returning the installed descriptor. This is distinct from the IMPORT branch's invalid put. A read-only but readable ioctl argument can permit copy-in and fail copyout; peer silence is unnecessary.

The next separate unit should reserve an fd, fill and copy the result while still owning the dma-buf, and install only after all fallible work succeeds. Linux 7.3 already exports `dma_buf_fd_install:807–824` specifically for this ordering. On failures, release the unused reservation and put the still-owned dma-buf exactly once; on success transfer it exactly once and perform no later accesses requiring that transferred reference. Refactor the ALLOC helper boundary as needed so outer copyout precedes publication. Do not attempt rollback by closing an already-published integer fd: a concurrent close/reuse can target another file.

Acceptance for that separate unit must execute the actual ioctl dispatcher and producer bodies with fd reservation failure, copyout failure/partial copyout, success, and a shared-fd-table close at publication. Check descriptor visibility and real reference ownership, plus existing mapping retention until matching RELEASED after failed setup. The twelve-patch version must fail the copyout-after-install case. Existing `import-unit/run-producers.py` extracts `vc_sm_cma_ioctl_alloc` but does not extract `vc_sm_cma_ioctl_admitted`; its `producer-shim.c:36` supplies a simplified fd boundary. Those historical passes do not cover this newly identified outer ioctl defect. Preserve their scope rather than relabeling them.
