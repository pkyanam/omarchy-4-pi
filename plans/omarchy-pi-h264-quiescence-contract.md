# Pi H.264 quiescence contract audit

November 8, 2026. Source research only. This audit does not qualify deployment, DMA safety, removal, or performance. The parent owns builds, physical access, integration and status reporting. No existing candidate, patch, recipe or progress file was edited; no compiler, Pi/SSH/GPU, Docker, VM, staging, commit, external message or subagent was used.

## Decision

The exact eleven-patch source preserves possibly firmware-owned mappings by waiting; it does not provide bounded cancellation or bounded removal. No usable firmware cancellation acknowledgement, transport-close-to-VCSM-quiescence guarantee, or reset-and-DMA-drain interface was found in the bounded source set below. Do not implement a timeout-to-free, reinterpret CLOSE as RELEASED, or issue ACTION_CLEAN on the strength of its header declaration.

This is a source-evidence limitation for a bounded recovery implementation, not proof that a cooperative firmware runtime experiment is impossible. A responsive-peer decode experiment and qualification under dead-peer teardown are different gates. The parent can continue compilation and lifecycle review independently. No runtime experiment is approved by this report alone: the candidate's other known lifetime/error-path gaps remain gates.

## What completion actually means

| Boundary | Established contract | Insufficient inference |
| --- | --- | --- |
| Ordinary kernel DATA queue returns nonzero before IMPORT publication | For the exact audited memcpy/ordinary-service path, producer can retire locally | Does not generalize to another transport or OPENSYNC |
| IMPORT response with zero handle | Definitive rejection in the candidate contract | Signal, malformed reply or lost reply is not rejection |
| IMPORT response with nonzero handle | Firmware has supplied the resource handle; candidate can associate subsequent ownership/release | Does not mean the device finished with the memory |
| FREE helper returns success | Command admitted to SMIO's queue | Not even proof of transport publication, much less firmware release |
| Matching RELEASED | Header defines VC completion with an allocation and release of Linux references; candidate matches original context, ID and confirmed handle | Does not drain unrelated generations or host callbacks |
| VCHIQ CLOSE/service retirement, SMIO worker join | Transport service/host execution lifetime boundaries | No demonstrated VCSM allocation or all-engine DMA drain |
| Deadline/signal | Caller should be able to stop waiting under a redesigned API | Supplies no memory ownership fact |

The [pinned VCSM definitions](https://github.com/raspberrypi/linux/blob/2569533d6c33c15231fbc21704c87fcebc67173c/drivers/staging/vc04_services/vc-sm-cma/vc_sm_defs.h) describe protocol version 2, IMPORT/FREE, and RELEASED. They explicitly say version negotiation failure requires either failing or avoiding reliance on RELEASED. The candidate's CLIENT_VERSION event sets `require_released_callback`; it is not currently an admission barrier, and 0011 retains firmware mappings even when that flag is false. Therefore old or mismatched firmware can allow an IMPORT but never supply the event needed to retire it. Prepublication capability/readiness rejection is a possible small future unit, subject to the actual acknowledgement semantics; it would avoid an unsupported-protocol case, not solve lost replies from supported firmware.

In exact `vc_sm_cma_vchi.c:429`, IMPORT waits with `wait_for_completion`, after queue admission. The worker completes it on definite queue failure or an exact-size matching response. A lost or malformed-only response leaves it pending. Stop waits for admitted IMPORTs before stopping the worker/service. The producer holds `sm_admission_lock` throughout admission; removal must acquire this lock. Consequently silence can block remove even before its live-buffer wait. After a successful response, client release/setup error sends FREE but the mapping remains live until matching RELEASED. These are two distinct unbounded waits.

The nonzero queue-return/nonpublication conclusion follows the audited ordinary `queue_message` path: validation/quota/slot/copy failures precede header/position publication; the kernel memcpy callback does not fail; after publishing `tx_pos` and signaling the remote event the ordinary path returns success. Existing import-unit documentation records that audit. This does not turn a successful queue return into a firmware acknowledgement.

## Normal Raspberry Pi driver architecture

The [pinned arm64 bcm2711 defconfig](https://github.com/raspberrypi/linux/blob/2569533d6c33c15231fbc21704c87fcebc67173c/arch/arm64/configs/bcm2711_defconfig) explicitly enables module unloading and builds VCHIQ into the kernel (`CONFIG_BCM2835_VCHIQ=y`), while camera, codec and ISP are modules. The matching 32-bit bcm2711 and bcmrpi defconfigs show the same split. [Codec Kconfig](https://github.com/raspberrypi/linux/blob/2569533d6c33c15231fbc21704c87fcebc67173c/drivers/staging/vc04_services/bcm2835-codec/Kconfig) selects MMAL, and [MMAL Kconfig](https://github.com/raspberrypi/linux/blob/2569533d6c33c15231fbc21704c87fcebc67173c/drivers/staging/vc04_services/vchiq-mmal/Kconfig) selects VCSM. With the inspected module-valued media selectors, MMAL/VCSM are module-selected; VCSM is not made built-in merely because VCHIQ is built-in. This is defconfig evidence, not verification of every distributed or running Pi OS kernel config. Parent should record the actual comparison image config/module list before a parity claim.

[VCSM Kconfig](https://github.com/raspberrypi/linux/blob/2569533d6c33c15231fbc21704c87fcebc67173c/drivers/staging/vc04_services/vc-sm-cma/Kconfig) is tristate. Its source uses `module_vchiq_driver` and has a remove callback labelled driver unloading. Thus “the normal driver is wholly built-in and cannot be unloaded” is incorrect. Conversely, having an unload entry point does not prove correctness with outstanding imports or a failed firmware peer.

In the [downstream implementation](https://github.com/raspberrypi/linux/blob/2569533d6c33c15231fbc21704c87fcebc67173c/drivers/staging/vc04_services/vc-sm-cma/vc_sm.c), version-2 operation retains `vc_handle` until RELEASED; legacy operation clears it without that callback. Its dma-buf release path unmaps an imported attachment before final allocation retirement. Its remove callback deregisters the misc/debug interfaces, stops SMEM and destroys state/IDR locks; it has no equivalent of this candidate's outstanding-buffer drain. The [downstream SMIO stop](https://github.com/raspberrypi/linux/blob/2569533d6c33c15231fbc21704c87fcebc67173c/drivers/staging/vc04_services/vc-sm-cma/vc_sm_cma_vchi.c) closes service handles and frees its instance. These are actual cleanup choices; they are not a documented firmware guarantee that close quiesces all imported DMA. Copying them would reintroduce lifetime questions rather than settle them.

Normal architecture remains V4L2 mem2mem codec → MMAL → VCSM dma-buf sharing over VCHIQ → firmware codec services. MMAL `port_disable` distinguishes locally queued buffers from buffers already passed to firmware and expects callbacks for the latter. Its synchronous control-message timeout even notes the late-response problem; it is not an all-buffer DMA-drain contract. Preserve kernel/userspace dma-buf APIs, normal decode/encode and applicable ISP/media functionality, cache/attachment semantics and platform transport ownership. A built-in-only workaround, removal suppression, feature hiding, or replacing MMAL with a different stack would be a deliberate departure requiring explicit justification and qualification, not an automatic parity fix. “Mainline architecture” also does not mean this downstream codec is already present in vanilla Linux 7.3.

## Cancellation, close and reset negative result

`ACTION_CLEAN` and `vc_sm_action_clean_t` exist in the protocol header as a generic action/transaction revert shape. There is no sender or handler for them in the inspected VCSM CMA implementation. No acknowledgement ordering, handling of an in-flight IMPORT, interaction with outstanding firmware references, or DMA-finished semantics was found. The unused `free_all` structure is equally insufficient. Neither is an implementable IMPORT cancellation contract from these sources.

The exact VCHIQ close state machine operates on services, CLOSE exchange, service messages and VCHIQ bulk queues. `abort_outstanding_bulks` completes transport bulk bookkeeping, including fabricated unmatched entries. VCSM IMPORT describes a bus address inside an ordinary SMEM DATA message; it is not registered as one of those VCHIQ bulk transfers. A bulk-abort path therefore cannot be promoted into a VCSM mapping drain. Candidate owner-reference completion additionally proves host callback/reference retirement, not firmware memory retirement.

Both inspected parent transport removals unregister child devices and stop host threads; the candidate's `vchiq_platform_uninit` has no firmware reset handshake. The inspected Linux mailbox firmware interface exposes VCHIQ initialization and power/execute tags, but no VCSM reset-and-drain API. A name containing reset, a generic power command, remote-event suppression, disabling an IRQ, `vchiq_shutdown`, or a host thread join does not establish that VideoCore and all consumers of its imported handles can no longer access RAM.

The [firmware repository README](https://github.com/raspberrypi/firmware/blob/ab5c7f86283ceb58b7adb269cae1d16092a31bf6/README.md) identifies precompiled GPU firmware binaries; this audit did not obtain the SMEM server implementation. The [userland import documentation](https://github.com/raspberrypi/userland/blob/a54a0dbb2b8dcf9bafdddfc9a9374fb51d97e976/host_applications/linux/libs/sm/user-vcsm.c) independently distinguishes host detachment from VideoCore retaining a buffer reference. It supplies no reset proof. A maintainer specification or matching firmware implementation would be needed to extend the result beyond the public host protocol.

Search was bounded to the exact candidate/reference C/headers, added pinned downstream VCHIQ/config/Kconfig files, selected Linux 7.3 driver-core/firmware files, and the VCSM userland files discovered in its pinned recursive tree. Terms and full matches are in `negative-search.log`. Three primary-domain web searches were also attempted for ACTION_CLEAN, module config and VCHIQ reset/close; they yielded no usable contract and were not used as proof. This is not an exhaustive search of all Raspberry Pi history, private firmware, mailing lists or hardware manuals, and does not assert that no such mechanism could exist.

## Design choices

| Choice | Memory safety requirement | Boundedness and feasibility |
| --- | --- | --- |
| Keep 0011's synchronous waits | Retain all owners/mappings until definite outcomes, plus prove other lifecycle paths | Conservative about uncertain DMA, but peer silence or an unclosed client can block forever; incomplete deployment contract |
| Return a bounded error and quarantine | Transfer the entire pending operation to durable ownership before caller unwind; preserve original transaction/generation, mappings, IDR, device/DMA context, module code, service worker and late-response handling | Can bound the caller; cannot guarantee bounded successful removal or bounded memory use. Exact current producer/admission ownership is synchronous and cannot simply return ETIMEDOUT |
| Prevent removal/unbind while retained | Exclude every actual teardown entry, including ancestor unregister, without releasing devres or executable callbacks | A policy constraint can preserve safety but is a feature/operability limitation. No veto exists in this bus's void remove callback |
| Genuine reset with DMA drain | Specify reset scope, completion and ordering, all bus masters/firmware consumers, outstanding writes and future access exclusion; retain resources until that condition, then retire old generation and isolate late events | Would permit reclaim and recovery if real; no supporting contract found here |

For quarantine, late success must acquire its handle and arrange FREE/RELEASED retirement without reviving a failed caller; lost reply remains quarantined indefinitely. Enforce an admission budget or fail the service closed to prevent repeated failures exhausting memory. Transaction/generation reuse cannot let late events target new buffers. This is a design obligation, not an implemented patch recommendation or proof that retaining a `get_device` reference preserves devm allocations/DMA configuration.

Linux 7.3 driver-core sources extracted into the evidence show that `device_remove` calls the bus remove callback, followed by unbind cleanup/devres release. Returning early from this void callback would let core cleanup proceed. `suppress_bind_attrs` suppresses sysfs bind/unbind files only; it does not block parent removal or driver unregister. Exported dma-buf module ownership protects some ordinary unload paths, but failed-export/quarantined objects need a separately demonstrated lifetime. A successful user request to unload is different from a bounded refusal before teardown begins; do not advertise refusal without an enforceable entry-point policy. No forced unload is safe evidence.

## Smallest justified next unit and parent gates

No cancellation/reset patch is justified by the source found. The smallest next deliverable for that blocker is a precise firmware/transport contract answer covering admitted IMPORT with lost response, outstanding imports after CLOSE, and reset completion versus all DMA users; absent that answer, select an explicit retained-ownership/error policy and acknowledge that bounded successful removal remains unsupported. Do not append speculative cancellation, reset and watchdog patches. If implementation resumes without new protocol evidence, a bounded caller-return/quarantine unit must first specify and prove independent ownership through late response and attempted teardown; it is a substantive lifetime refactor, not changing one wait primitive.

The peer-silence issue alone forbids claiming bounded cancellation, dead-peer recovery or safe successful teardown under missing acknowledgements. It does not logically forbid cooperative-path runtime testing with storage retained on uncertainty. For a parent-controlled experiment:

1. Finish exact-series combined module build/modpost and validate the actual target ABI/config. Existing READMEs say 0007–0011 were uncompiled when written; this researcher did not check or change the parent's evolving build state. Build success does not settle lifetime safety.
2. Review the remaining connected-init allocation failures, VC_MEM_REQUEST response errors, FREE publication/failure policy, debugfs admission, and ancestor teardown ordering. Some can occur during normal initialization/operation. The peer-silence conclusion does not waive them or declare the whole candidate safe.
3. Establish recovery before loading: the parent must be able to leave mappings pinned and recover the whole machine if a task sticks in uninterruptible wait. A userspace timeout or SIGKILL is observation/control of the supervisor, not cancellation of the kernel operation. Do not depend on `rmmod`, unbind or orderly reboot completing after a hang; arrange physical recovery and storage protection under the parent's authority.
4. Verify matching firmware/service protocol support; observe responsive IMPORT and matching RELEASED on the exact generation for normal client close, setup failure and stream shutdown. Preserve raw events/state and mapping lifetimes. A successful decode demonstrates only the exercised path.
5. Keep removal/reprobe/unload and dead-peer/lost-reply testing as separate destructive lifecycle qualifications with recovery ready. No forced freeing, timer-based reclamation, intentional parent transport disruption on an unprotected machine, or success claim based on lack of a visible crash.
6. Treat normal repeated decode/encode, close/reopen and applicable media features as functional gates; compare performance to a matched Pi OS image only after correctness. No Pi 5, 8GB, power or parity claim follows from this audit.

This research ran no new host tests. A host stub that invents cancel/reset acknowledgement or DMA cessation would only test the invented boundary and cannot close this blocker.
