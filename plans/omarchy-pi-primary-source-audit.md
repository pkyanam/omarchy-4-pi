## BCM2711 crypto: unavailable instructions are not a configuration defect

The [Arm Cortex-A72 product page](https://support.arm.com/compute-ip/cortex-a72) identifies Armv8-A; the separate [Arm cryptography engine manual](https://support.arm.com/documentation/100097/latest/introduction/about-the-cortex-a72-processor-cryptography-engine) describes the crypto engine, not a guarantee that every A72 SoC implements it. The [Raspberry Pi launch-era BCM2711 crypto discussion](https://forums.raspberrypi.com/viewtopic.php?t=243410) contains a contemporaneous staff response that crypto instructions were not available as far as the responder could determine. Full direct retrieval returned HTTP 403 during this audit; indexed thread text was available. A later participant's attribution of a stronger statement to James Hughes is second-hand, so it is not treated as independently verified manufacturer silicon documentation. Together with the recorded feature list, expected unavailability is a much stronger working interpretation than a newly discovered EL2 masking defect. No die/fuse/licensing explanation is established here.

The authoritative software contract is [arm64 ELF HWCAP](https://docs.kernel.org/arch/arm64/elf_hwcaps.html): AES, PMULL, SHA1, SHA2 and atomics have separate ID-register-derived flags. CRC32 does not imply any of the others. LSE is also not inferred from the A72 name. An EL2 startup message describes the entry exception level; it does not demonstrate a resident hypervisor emulating Linux's ID registers or show any feature was removed. A firmware masking diagnosis would need a concrete masking implementation or differing trustworthy register evidence, neither of which the discovery provides.

The local [AES glue](https://github.com/torvalds/linux/blob/c03c1a14507dfaf8b856c2608f9ac216021fc222/arch/arm64/crypto/aes-glue.c#L721) uses `module_cpu_feature_match(AES, aes_init)` for the CE build. [GHASH glue](https://github.com/torvalds/linux/blob/c03c1a14507dfaf8b856c2608f9ac216021fc222/arch/arm64/crypto/ghash-ce-glue.c#L385) returns `-ENODEV` without ASIMD and PMULL. The discovery's failed loads are consistent with correct capability gating; packaging CE modules on a shared aarch64 kernel does not mean the board can execute them.

The candidate config also provides `CONFIG_CRYPTO_AES_ARM64_NEON_BLK=m` and `CONFIG_CRYPTO_AES_ARM64_BS=m`. Inspect `/proc/crypto` for the actual registered XTS driver and priority before assuming generic scalar AES is selected. NEON software crypto remains software crypto even when substantially faster than a scalar fallback. Never override HWCAP/ID bits or bypass module checks. Keep the current LUKS cipher, key size, sector size, integrity and durability posture. AES-CBC in OpenSSL, AES-XTS in cryptsetup's memory benchmark and actual dm-crypt filesystem throughput are different measurements; none alone establishes the SSD ceiling.

## CPUFreq: the displayed driver is expected; the clock fall is unresolved

In the exact [Raspberry Pi CPUFreq source](https://github.com/torvalds/linux/blob/c03c1a14507dfaf8b856c2608f9ac216021fc222/drivers/cpufreq/raspberrypi-cpufreq.c#L39), lines 43–48 round the firmware-backed clock's min/max and add OPPs dynamically at 100MHz intervals. Line 53 registers `cpufreq-dt`. These runtime OPPs need not appear as static firmware-tree `opp-*` nodes. Both the module and displayed driver can therefore be correct simultaneously. The candidate config selects Raspberry Pi CPUFreq as a module and defaults to schedutil; the running governor still needs observation.

The exact [firmware clock driver](https://github.com/torvalds/linux/blob/c03c1a14507dfaf8b856c2608f9ac216021fc222/drivers/clk/bcm/clk-raspberrypi.c) explicitly retains firmware over-temperature and under-voltage protection. [Raspberry Pi frequency-management documentation](https://www.raspberrypi.com/documentation/computers/raspberry-pi.html#frequency-management-and-thermal-control) describes independent firmware throttling. A 110°C Linux trip is not its threshold. The reported 51–54°C sample does not by itself prove thermal throttling either; voltage, timing, requested frequency, actual clock and workload state remain needed. [CPUFreq documentation](https://docs.kernel.org/admin-guide/pm/cpufreq.html) cautions that `scaling_cur_freq` often reflects the requested P-state rather than an independent hardware measurement.

Absence of `vcgencmd` is not proof that all firmware telemetry is unavailable. The exact [raspberrypi-hwmon source](https://github.com/torvalds/linux/blob/c03c1a14507dfaf8b856c2608f9ac216021fc222/drivers/hwmon/raspberrypi-hwmon.c) uses `RPI_FIRMWARE_GET_THROTTLED`; the candidate has `CONFIG_SENSORS_RASPBERRYPI_HWMON=m`. Enumerating existing hwmon devices/attributes is read-only; loading a missing module is a separate state-changing experiment. Check binding and read errors, not merely config presence. An undervoltage alarm is not necessarily a complete current/historical throttle bitmap. The source polls every two seconds and requests clearing sticky bits (`value = 0xffff`); loading it can therefore change telemetry history. Coordinate collectors and capture existing state before a module-load trial, rather than claiming this is a passive addition.

## KPTI: Meltdown status and KASLR hardening are separate

The exact [arm64 feature source](https://github.com/torvalds/linux/blob/c03c1a14507dfaf8b856c2608f9ac216021fc222/arch/arm64/kernel/cpufeature.c#L1833) lists all Cortex-A72 versions as Meltdown-safe (line 1848), then separately forces isolation when KASLR requires it (1884–1889). The [MMU helper](https://github.com/torvalds/linux/blob/c03c1a14507dfaf8b856c2608f9ac216021fc222/arch/arm64/include/asm/mmu.h#L85) accounts for E0PD where present; otherwise it returns that KPTI is required for this purpose. The saved config enables both `CONFIG_UNMAP_KERNEL_AT_EL0=y` and `CONFIG_RANDOMIZE_BASE=y`. “Not affected” for Meltdown is consistent with this path and does not make KPTI redundant. Other vulnerability files are not collectively evidence about Meltdown or this hardening decision.

The parser at lines 1990–2001 accepts `kpti`; the matching [kernel-parameter reference](https://github.com/torvalds/linux/blob/c03c1a14507dfaf8b856c2608f9ac216021fc222/Documentation/admin-guide/kernel-parameters.txt) documents arm64 `kpti=0/1` and x86 `nopti` / `pti=` separately. Cmdline text alone does not establish the effective mitigation. Preserve unknown if boot logs/config are unavailable. Keep KPTI, KASLR and existing Spectre/BHB mitigations for the recommended experiments. Any later explicit mitigation-cost diagnostic with `kpti=0` would reduce KASLR hardening and is outside this report's security-preserving experiment set; do not ship it as a tuning default or disable KASLR to facilitate it.

## Zram: compression, physical usage and writeback are separate

The exact [zram reference](https://github.com/torvalds/linux/blob/c03c1a14507dfaf8b856c2608f9ac216021fc222/Documentation/admin-guide/blockdev/zram.rst) and [driver](https://github.com/torvalds/linux/blob/c03c1a14507dfaf8b856c2608f9ac216021fc222/drivers/block/zram/zram_drv.c) describe compressed pages stored in RAM. Root-volume encryption is not inserted into that RAM path. An explicitly configured encrypted swap mapping or backing device would be a separate topology. Because the candidate enables `CONFIG_ZRAM_WRITEBACK=y`, capture `backing_dev` and `bd_stat` before asserting RAM-only operation; config support does not mean writeback is active. Do not add unencrypted disk backing as a performance workaround.

The resolved config really enables zstd and chooses it as the default, alongside LZO/LZ4 and other backends. The older ALARM config claim cannot describe this candidate. The bracketed `[zstd]` in the saved live observation identifies the selected compressor, while `disksize=3924819968` means logical capacity, approximately 3.66GiB, not physical allocation. Discovery's later description of the live device as half-RAM contradicts its own full-size observation. `mm_stat` must establish actual usage; available RAM and compressed swap capacity are not additive budgets. `swappiness=150` is a policy weighting, not a literal percentage of RAM swapped. Candidate zswap defaults on, so the recorded `zswap.enabled=0` should be verified against the running parameter rather than assumed from the build config.

## Media: downstream codec source was mislabeled as mainline

The tar archive contains no `bcm2835-codec`, `bcm2835-isp` or `rpivid` source paths. The exact [upstream staging Kconfig](https://github.com/torvalds/linux/blob/c03c1a14507dfaf8b856c2608f9ac216021fc222/drivers/staging/vc04_services/Kconfig) sources only BCM2835 audio. The saved codec Kconfig's manifest instead identifies [raspberrypi/linux at `2569533d6c33c15231fbc21704c87fcebc67173c`](https://github.com/raspberrypi/linux/blob/2569533d6c33c15231fbc21704c87fcebc67173c/drivers/staging/vc04_services/bcm2835-codec/Kconfig), recorded as `rpi-6.12.y`. In this upstream version VCHIQ itself lives under [drivers/platform/raspberrypi](https://github.com/torvalds/linux/blob/c03c1a14507dfaf8b856c2608f9ac216021fc222/drivers/platform/raspberrypi/Kconfig), alongside a separate MMAL service option. Its transport and userspace character interface are prerequisites for some multimedia paths, not codec implementations. The downstream codec dependency cannot create a driver absent from the upstream source. This corrects both PI-015 and discovery without editing either ledger.

The exact [Unicam Kconfig](https://github.com/torvalds/linux/blob/c03c1a14507dfaf8b856c2608f9ac216021fc222/drivers/media/platform/broadcom/Kconfig) does support CSI-2 capture independently of VC4 firmware. The config currently disables it. Enabling it is only a build prerequisite: sensor driver, DT endpoint/clock/regulator graph, physical sensor and userspace pipeline are still necessary. It does not decode H.264 or HEVC. The separately disabled [BCM2835 audio option](https://github.com/torvalds/linux/blob/c03c1a14507dfaf8b856c2608f9ac216021fc222/drivers/staging/vc04_services/bcm2835-audio/Kconfig) selects VCHIQ; VC4 HDMI ALSA/ELD is another path.

Saved absence of `/dev/video*` and `/dev/media*`, together with missing Pi codec sources/config, supports “no demonstrated usable Pi V4L2 hardware decode path in this candidate.” It should not be generalized into a universal theorem about every hardware decode API. `ffmpeg -hwaccels` lists compiled interfaces, not working decoders. V3D rendering, VCHIQ transport, capture, ISP, decode and browser integration require separate evidence. Prefer upstreaming the missing codec support with matching maintainers; only consider a maintained downstream patch/kernel candidate if upstream support cannot presently be delivered, documenting that reason and its update/security obligations. Never copy foreign-ABI Pi OS modules.

## PCIe: keep Pi 4 and Pi 5 advice separate

[VIA's VL805/VL806 specification](https://www.via-labs.com/product_show.php?id=48) states PCI Express 2.0 x1. Raspberry Pi's [BCM2711 Compute Module 4 hardware documentation](https://www.raspberrypi.com/documentation/computers/compute-module.html) describes its Gen 2 interface; this is corroborating SoC-family information, not a CM4 result substituted for the tested Model B. The candidate's [PCIe driver](https://github.com/torvalds/linux/blob/c03c1a14507dfaf8b856c2608f9ac216021fc222/drivers/pci/controller/pcie-brcmstb.c) supports several SoCs: parsing a maximum link generation up to 3 does not establish that BCM2711 and its VL805 endpoint can negotiate it. The recorded 5GT/s x1 is the expected Gen 2 link. [Official Gen 3 tuning guidance](https://www.raspberrypi.com/documentation/computers/raspberry-pi.html#pcie-gen-3-0) concerns Pi 5, with a stability warning even there.

Do not try `pciex1_gen=3` on this SSD path. Gen 2 has 500MB/s per-direction capacity after 8b/10b coding and before PCIe transaction overhead; USB protocol, shared ports, bridge, filesystem and crypto reduce realized throughput. Neither that theoretical capacity nor the observed link speed proves PCIe is the current bottleneck. Likewise `usbfs_memory_mb` is not automatically a bound on kernel UAS/block transfers; require actual transport/error evidence before changing it.

## Experiments for the parent: security-preserving and bounded

All experiments below are proposed, unexecuted, and owned by the parent. First repair the recorder/probe defects described in kickoff, preserve unknown values, and start a versioned series rather than mixing changed semantics with the existing six baseline rows. Capture exact package/source/firmware versions, boot ID, UTC time, board/RAM identity, workload hashes and active policy. Keep this 4GB board separate from 8GB and Pi 5.

No EEPROM flash, overvolt, disabled barriers, unencrypted spill, forced CPU features or global compiler flag changes are part of these experiments.
