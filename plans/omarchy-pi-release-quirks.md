# Omarchy native Pi release: quirk and qualification ledger

Updated 2026-11-07 (America/New_York). This is the working ledger for the proposed upstream Raspberry Pi integration, not a claim that the native Pi release is ready. Record a new observation here before turning a test-machine workaround into release behavior. A fix is complete only when its source/package ownership, fresh installation, upgrade, and rollback paths are accounted for.

## Target and evidence boundary

The current physical test is a Raspberry Pi 4 Model B Rev 1.5, hardware revision `c03115`: the 4GB model according to Raspberry Pi’s official revision table. Earlier descriptions as an 8GB board were an unchecked assumption and are corrected here. It runs the unpublished `linux-omarchy 7.3-32` candidate. PFTF v1.53 firmware now boots from the 8GB firmware-only microSD card (storage capacity, independent of board RAM); the original 128GB installer card is retained for recovery. Omarchy is installed on a 500GB USB SSD with LUKS and Btrfs. After the owner disabled the 3GiB limit, SSH confirmed `RamLimitTo3GB=0`, Device Tree mode, and `MemTotal: 3832948 kB` (about 3.7GiB usable), with approximately 1.5GiB in use. This is an uncapped 4GB boot, not an 8GB-board result. Sustained uncapped stability, the actual 8GB board, and all Pi 5 models remain unqualified.

The upstream runtime, package, and installer work is in the local `pi4-aarch64` branches of `omarchy-upstream-pi`, `omarchy-pkgs-pi`, and `omarchy-iso-pi`. The published community v4.5.0 image uses a different U-Boot/ALARM kernel path. Its prior successes, package policy, Bluetooth work, and performance claims cannot certify this new UEFI → Limine/UKI path. No upstream PR or push is authorized yet.

Local evidence is retained under `build/upstream-pi/` in this checkout. That directory is ignored by Git; preserve the relevant logs, hashes, screenshots, and package manifests with the eventual review/release evidence rather than committing private machine dumps or diagnostic access material.

The delivered `.img` and ISO have not been rebuilt with these installed-machine repairs. Rebuild, audit, and hash the release artifacts after the fixes are incorporated into their proper source/package owners. Do not relabel the existing diagnostic card or image as the final release.

## Release gates still open

1. Publish a coordinated, supported kernel/runtime/settings/support-package/installer set; remove test-only holds and diagnostic artifacts.
2. Qualify physical Pi 4 4GB and 8GB boards independently, with full usable RAM and measured performance/power.
3. Complete native HDMI/EDID, audio playback, Wi-Fi connection, Bluetooth pairing/reconnect, USB storage, lock/wake, and media tests.
4. Test a real kernel/package upgrade, subsequent encrypted cold boot, interrupted-update recovery, and root plus ESP rollback.
5. Test installer disk hotplug/revalidation and a fresh installation from the actual release artifact.
6. Define firmware-media ownership, supported firmware revision, updates, boot order, and recovery without hidden per-machine edits.
7. Reconcile visible release identity and package versions; provide a tested transition from the community distribution or explicitly require backup/fresh install/data restore.
8. Keep Pi 5 excluded until its own kernel, firmware, boot, graphics, storage, radios, and RAM variants are physically qualified.

## The install is waiting on a password, not on a decision — November 8, 05:20 UTC

The owner authorized install-and-reboot. It could not be started, for a reason worth recording so nobody re-litigates it: `preetham` has **no passwordless sudo** on this Pi. `sudo -n true` fails, the only `NOPASSWD` entries are narrow command patterns (`asdcontrol`, `omarchy-dns <provider>`, `omarchy-locale-generate <locale>`, `omarchy-theme-set-browser-policy <hex>`, `timedatectl set-timezone <zone>`), none covers `pacman` or `snapper`; there is no live sudo timestamp; root SSH is denied; and `pkexec` needs a controlling terminal that an `ssh` command does not supply. **One dead end was closed today, which is worth more than it looks.** `btsdio` is loaded on this machine and it was tempting to hope a Bluetooth controller might appear through SDIO without the UART work. It will not. `btsdio` matches SDIO class `0x02`/`0x03`; the 43455 combo card reports class `0x00` on `mmc1:0001:1` and `:2`, and class `0x02` only on `:3` — which has no driver. The Bluetooth function `mmc1:0001:2` (id `0xa9a6`) is bound by `brcmfmac`, correctly. So this board's Bluetooth is UART-only and the `btsdio` load is harmless noise. Related trap: `mmc@7e300000` reads `disabled`, but the card actually runs on `fe300000.mmcnr`; the `mmc` alias points at the disabled node while `mmc1` is the live one. Wi-Fi demonstrably works there, so that `disabled` is not a defect to fix.
