# Controlled browser THP experiment — prepared, not measured

November 8, 2026. This independent lane owns only this document and `tools/pi-experiments/thp-browser-*`. Read root AGENTS, kickoff, progress through candidate 2.6 and the low-level plan/tools. No subagents, SSH, Pi execution, browser opening, benchmark, installation, build, policy write, staging, commit, push, PR or external message was performed. This adds experiment instrumentation only, with no product daemon or timer.

## Question and acceptance gate

Does changing only runtime top-level THP `enabled` from `always` to `madvise` improve browser tail latency or retained browser memory on the native **4GB Pi 4** while preserving the same desktop? All measured claims are pending. No 8GB, Pi 5, Pi OS comparison, energy result, release qualification or default-policy recommendation follows from these source artifacts.

The earlier [low-level plan](omarchy-pi-low-level-next-experiments.md) requires an owner-derived real daily corpus. This deliverable is a fixed self-contained **representative-shaped fixture**, ready for owner review, not proof of daily-workload representativeness. Parent must accept its document/dashboard/editor mix against actual daily use before calling it representative. It does not reproduce a PDF renderer, external web app, real service latency, video, downloads or an extension-heavy session. If PDFs or those behaviors dominate daily use, stop and prepare a separately versioned local corpus before A/B; do not describe this fixture as covering them. Do not add allocation balloons to manufacture pressure.

Keep baseline unless a baseline replay first demonstrates meaningful memory pressure (predeclare either memory-some PSI at least 1% over replay or at least 64 MiB new zram original payload, with correlated browser growth). If pressure is absent, close this experiment as insufficient excitation. This is an eligibility gate, not a benchmark result or a reason to increase tab count. Also stop if explicit application advice dominates THP behavior or per-size modes defeat the intended inherited-policy comparison.

## Fixed corpus and interaction contract

[thp-browser-page.html](../tools/pi-experiments/thp-browser-page.html) is one immutable local page parameterized by tab index 0–11. The fixed order repeats documentation, dashboard and notebook four times. Each page contains 64 deterministic sections, ordinary text/DOM layout, a working text field and either eight-row tables or code excerpts. No random values, remote assets, artificial heap allocation, workers, audio, video, service workers, timers or ongoing animation. CSP blocks external resources and page connections. It deliberately uses the installed monospace fallback rather than fetching a font; record the resolved font/font packages in context and freeze them across trials. This is a frozen test fixture, not a project typography change.

The runner serves only `/corpus?tab=N` on loopback port 8765, 12 tabs maximum. No external page content is replayed. Parent must ensure external networking is unavailable before browser startup using an existing controlled offline environment, preserving loopback and the desktop. Page CSP alone does not prevent Chromium background networking. The runner does not change firewall, networking, browser sandbox, site isolation, GPU policy, memory saver, zram, CMA, mitigations, governor, compositor, wallpaper, display mode, idle policy or other services. If offline isolation cannot be established and documented without disrupting the parent session, defer the run. Do not add `--no-sandbox`, single-process, renderer limits, GPU-disabling or background-throttling flags.

Normal installed headed Chromium starts a brand-new empty `--user-data-dir` for **every** trial, including consecutive B trials. The seed is the empty directory (SHA-256 of zero bytes in manifest); no personal profile, extensions, cookies or previous allocations are reused. First-run/default-browser prompts are suppressed with fixed flags, and loopback CDP is enabled only for the private process. Chromium platform policy and built-in component state still apply; parent must capture them. The wrapper launcher hash alone does not identify the actual Chromium ELF: record package version, executable path/hash, shared-library versions and policy separately. Twelve same-origin tabs may share renderer processes under normal architecture; do not force a process count or infer 12 renderers. Warm caches are not dropped.

Readiness waits for fixture construction, not a fixed loading sleep. Trace begins after a before snapshot. Starting at tab 0, the fixed replay visits tabs 1 through 10 (ten foreground switches). Each visit sends PageDown twice, PageUp twice via CDP keyboard input, returns to the top, focuses the note and inserts the same 17-character text. It finishes by revisiting tab 0. Tab 11 remains a loaded background retention tab. No concurrent user input, tab management, window occlusion, lock, DPMS, popup, devtools window or browser resizing is permitted. The CDP input path is repeatable browser input; it does not measure physical keyboard-to-screen latency. All actions have unique page `performance.mark` trace tags and host monotonic dispatch/return stamps. Up to 61 actions are recorded, including 11 activations, 40 scrolling keydowns and 10 insertions. Key-up commands are also dispatched. No action starts after the 120-second active bound; a one-second watchdog and CDP request timeout bound a hung action. Whole setup/replay has a 180-second watchdog; cleanup/trace drain has separate short bounds.

## Prepared runner and dependencies

[thp-browser-trial.py](../tools/pi-experiments/thp-browser-trial.py) is an owner-run Python CLI. It has no policy-writing code, package installation, SSH or shell subprocess. The only launched program is the explicit installed Chromium path. Requires Linux, the current non-root graphical desktop, Python 3, an **already installed** `websocket-client` Python module, readable `/proc`/THP/thermal/native voltage telemetry, an available loopback port, and the adjacent [low-level snapshot tool](../tools/pi-experiments/low-level-snapshot.py). Missing dependencies are a pending gate, not installation authority. No Python/CDP dependency was installed or browser launched here.

Before launching, create an immutable private JSON context file containing: board model/revision and actual MemTotal; running kernel/config/package/build identities; boot ID; repository heads/dirty status and tool hashes; actual Chromium ELF/package/launcher/version and policies; Python and websocket-client versions; font resolution; desktop/shell/compositor versions/PIDs; physical output mode/scale and window dimensions/position; CPU governor and cooling; current memory/zram/swap/CMA settings; background process inventory; network-isolation method; corpus acceptance rationale; primary metric and pressure gate; tracing categories/overhead mode; start-temperature window; native voltage/firmware telemetry availability; error-log capture paths; idle-policy state; disk space and recovery/abort operator. Use no credentials, personal URLs, environment dump or encrypted-mapping keys. SHA-256 that JSON outside timing and use the same file for all twelve trials, recording trial-specific health separately. The runner embeds its parsed contents; retain and hash the original bytes too.

Future parent invocation, as the desktop user in a visible terminal (paths and PIDs must be actual, no literal placeholders):

```bash
python3 tools/pi-experiments/thp-browser-trial.py \
  --chromium /usr/bin/chromium \
  --context /absolute/private/context.json \
  --output /absolute/private/block1-A1 \
  --label block1-A1 --policy always \
  --pid 1234 --pid 5678 --start-min 40 --start-max 48 \
  >/absolute/private/block1-A1-console.log 2>&1
```

The output parent directory must exist; the trial directory must not. Use real shell/compositor PIDs. Predeclare a temperature window at most 8°C wide, identical across trials; the example window is proposed, not verified attainable. Also require paired start temperatures within 2°C; if not, reject the block. Do not cool by changing governor or desktop. Prepare and validate one excluded baseline calibration replay first, including trace presentation correlation, browser sandbox status, window state, health stops and cleanup. This lane did not execute it.

## Policy transaction: parent only

Save the complete THP control hierarchy before any write, bracket-selected values, original top-level mode, defrag, every `hugepages-*kB/enabled`, shmem and khugepaged controls, plus root's current session/provenance snapshot. If original mode is not `always`, stop and redesign. Read the matching kernel semantics: explicit per-size `always` is rejected by the runner; other explicit modes still require review. An inherited size must actually change eligibility, otherwise the comparison is not justified. `madvise` neither splits existing hugepages nor forbids explicit app requests/MADV_COLLAPSE. Fresh browser profiles/processes address old browser allocations; shell/compositor allocations remain a constant, not a full-session policy test.

In the parent's visible terminal, install an EXIT/HUP/INT/TERM restoration trap **before the first policy write**, using `sudo` for just the top-level sysfs write. Keep the trap active over the whole series. Authenticate/validate restoration authority before starting. Write only `always` or `madvise` to `/sys/kernel/mm/transparent_hugepage/enabled`, reread and verify the selected bracketed mode before each browser launch. Do not run the browser as root. A parent-approved transaction wrapper must restore the saved original top-level value on every exit, reread it, compare the complete non-counter hierarchy to its original snapshot, record success/failure and return failure if restoration fails. A failed or interrupted run remains in evidence; restoration must happen even when runner exits nonzero. Never write defrag, per-size controls, drop_caches, compact_memory, swappiness, CMA or zram during this transaction. Do not install persistent sysctl/kernel defaults. This document intentionally does not provide an unattended root wrapper: the parent owns the physical transaction and privilege boundary.

Use three blocks, each A1/B1/B2/A2, A=`always`, B=`madvise`, twelve fresh profiles total. Permit no overlapping build, perf, media, radio, GPU, package or display experiment. Same boot/session, software, output/window, network, trace categories and cold-profile initialization. Keep cache history controlled through ABBA ordering; do not call it cold-cache testing. ## Counters and timing interpretation

Artifacts per trial: `manifest.json`, `chromium.log`, `samples.jsonl`, `before.json`, `after.json`, `actions.json`, `page-00.json` through `page-11.json`, `trace.json` (or partial trace), console log, retained private `profile/`. Manifest includes boot/kernel, command, tool/corpus/snapshot hashes, declared policy, actual before/after hierarchy, browser CDP version, owner context, health, monotonic stamps, collection status and acceptance still pending. Chromium log/profile may contain machine details; do not publish raw files automatically.

One-second bounded samples record dynamic browser-main descendants (renderers, zygotes, GPU and utilities), per-process RSS/anonymous/file/swap, memory PSI, meminfo, vmstat and temperature/native voltage alarms. No missing process value is zero. Main RSS alone is invalid; aggregate RSS double-counts shared pages. PID races and exited children must be reported; boundary snapshots add stat/start identity, PSS, VmFlags, AnonHugePages, THP eligibility, mapping page size, process CPU ticks, fault counters and system block/zram/CMA accounting. These sequential snapshots are outside active replay; collection overhead is not atomic or free. The inventory follows parent links and cannot prove inclusion of reparented/orphaned browser tasks. Parent must verify process ownership/membership independently at calibration and reject unexplained omissions. Existing personal browser processes are excluded.

Compute before/after deltas for memory-some/full PSI `total` in microseconds divided by matching snapshot monotonic elapsed seconds × 1,000,000 (snapshot `elapsed_ns` is collection cost, not interval duration; use recorded `monotonic_start_ns`/`monotonic_end_ns` boundary stamps and report collection uncertainty). Samples supply active-phase monotonic points; use those for replay PSI rates, with uncertainty up to the sample period. Never subtract PSI averages or compare totals accumulated over different durations. Also report compact_stall/success/fail, allocstall*, thp_fault*/collapse*/split*, pswpin/out, pgscan/pgsteal, OOM and available CMA allocation failures, zram orig/compressed/allocator bytes, browser RSS peak and boundary summed PSS with missing-task accounting. Keep system-wide attribution and GPU/shared-memory limitations explicit. No free-CMA sample proves GPU consumption or need for more CMA. Optional perf repetitions are separately labeled, equally bounded and never mixed with unprofiled trials.

Trace categories are fixed in the tool. Calibrate against the installed Chromium trace schema before A/B. For each unique action tag, correlate its dispatch/renderer/input flow to the corresponding compositor frame submission and **presentation feedback** in the trace, accounting for process clock alignment and frame IDs. Activation can include browser/compositor latency before the target page's own work. A nearby Paint, RAF, DrawFrame, screenshot completion, CDP round trip or arbitrary next frame is insufficient. Preserve the mapping table with event/flow IDs and rejected/ambiguous samples. If a presented-frame endpoint or unambiguous linkage is unavailable for an action class, mark presentation latency unknown and fail the latency acceptance gate. Do not replace unknowns with RAF proxy durations. `actions.json` double-RAF stamps only detect scheduling stalls and visible targets. Event Timing entries are thresholded/quantized (minimum threshold 16ms), exclude fast events and may omit CDP text insertion or tab switching; they cannot supply a complete latency distribution. Long-task entries are diagnostic only.

Report p50/p95/p99 and maximum separately for activation, scrolling and editing, with raw sample counts and nearest-rank quantile rule. Eleven activation and ten editing samples per trial make p99 effectively a maximum; p99 is descriptive and cannot establish a small tail improvement. Do not pool unlike actions or independent trials to inflate confidence. Predeclare scroll action-to-presentation p95 as the proposed latency primary, boundary browser PSS as the memory primary/guardrail; select exactly one adoption primary before calibration results are inspected. For each block compare mean A trial metric with mean B trial metric; report all raw trial metrics, per-block relative differences and spread, never only pooled best-case numbers.

## Stops, mismatches and decision

Runner stops on native voltage alarm or unreadable health telemetry, temperature at/above 75°C, sampled new system OOM kill, browser startup/readiness/CDP/trace error, timeout or loss of foreground visibility. Trace output is capped at 256 MiB. Parent independently stops immediately for lock/DPMS, broken or stalled desktop, new kernel allocation/storage/USB/DRM/browser crash error, disk space below 1 GiB, unexpected background work or input, and power/cooling changes. Record before/after journal cursor and corresponding error review; runner does not claim complete journal monitoring or detect between-sample transients. Firmware throttle/actual clocks and energy remain unknown unless separately captured identically. Ctrl-C/TERM causes cleanup; SIGKILL, power loss and interpreter failure require the parent's separate restoration path.

Reject a trial/block for incomplete or dropped trace, incomplete action/page outputs, mismatched corpus/tool/context/package/ELF/font/policy/boot/window/network/idle state, reused/nonempty starting profile, different tracing/perf overhead, extra/missing tab, background/discarded page, process inventory omissions or unreadable PSS, unmatched initial memory (proposed maximum 64 MiB MemAvailable difference within a block), start temperature mismatch over 2°C, swapped workload steps, unexpected policy change, health/error stop, unverified cleanup/restoration or missing presentation correlation for the latency gate. Record window geometry and page visibility externally; CDP visibility alone cannot prove the desktop was unobscured. Collection success is never automatic acceptance. Retain all rejected trials and state why.

Advance only to a later owner-controlled full-session validation if all three accepted blocks agree on at least 10% lower primary p95 presentation latency **or**, if memory was predeclared primary, at least 64 MiB lower aggregate browser boundary PSS. Require at most 5% regression in the other primary metric and active replay duration, no new OOM/allocation/error, and no memory-full PSI rate increase above 5% relative; if baseline full PSI is zero, require zero observed candidate full PSI (no division by zero or invented epsilon). PSS benefits need comparable action-to-presentation latency too: unknown latency fails either adoption path. If pressure is absent, latency resolution inadequate, explicit app advice dominates, results disagree or any safety/behavior guard fails, retain `always` and report negative/inconclusive results. No default changes are authorized by this lane.
