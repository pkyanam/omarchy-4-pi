Parent reviewed exact Linux 7.3 arm64 ABI/source, verified the running config against matching headers, validated all eleven installed event formats without rebinding, then ran one 12-second capture guarded by the reviewed format hash. The corrected raw control-file write registered unchanged probe definitions successfully. The earlier EINVAL came from append-mode control-file I/O, not demonstrated rejection of a probe/register expression; its failing syscall remains source-inferred rather than directly traced.

All eighteen events and zero-hit RX probes are retained in observations.json; only task names/PIDs, raw addresses and absolute monotonic timestamps are omitted. No truncation, per-CPU drops/overruns or kprobe misses were reported. Global before/after state matched exactly, all owned probes/instance were removed, binding restored, taint stayed zero, post-temperature 47.225°C and native voltage alarm zero. The helper's physical_evidence=false means no electrical measurement is claimed.

Observed software sequence: power-off calls returned zero; flow disabled with RTS-clear request mask4; power-on returned zero after approximately121ms; flow enabled with RTS-set request mask4; initial host setter requested and reported115200. The tty adapter then accepted10/10 bytes and, roughly2.047seconds later,4/4 bytes. Prior btmon identified these lengths as vendor baud command and Reset; this capture logs no payload and does not independently decode command opcodes. No selected tty or Broadcom RX callback fired. No host230400 setter call was observed.

This establishes complete tty acceptance at the initial local termios rate, not physical UART transmission, FIFO draining, effective CTS, signal rate, controller power/reset or radio readiness. It narrows the next experiment to UART progress/flow/RX and electrical boundaries. Do not treat another baud-order or firmware patch guess as established. The radio still fails initialization.
